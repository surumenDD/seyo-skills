# chosei-seyo

図鑑は、AI の文章や進め方への利用者の指摘を原文のまま集めた文書である。文書の種類と主題の見出しの下に引き、プロジェクトごとに置く。分量の上限は設けない。書く側のエージェントは、二つの層（ronjutsu-seyo と buntai-seyo）を読んだあとに、図鑑のうち書く文書の種類の節と「進め方」の節を読む。共通の図鑑だけは全体を読む（6 節）。

このスキルは、会話から指摘を取り出して照合し、全件を控えに足す。そのうち残す価値のある原文を、登録の担当が図鑑の案に引く。図鑑への設置は、案を利用者に示して了承を得てから行う。

このスキルで使う語は次のとおりである。

| 語 | 意味 |
|---|---|
| 控え | 取り出した指摘の全件の記録（`entries.jsonl`）。照合と復元に使い、書く側は読まない |
| 回 | 1 回の取り込みの単位。名前は日時でよい（例：`2026-05-20-1430`） |
| 担当 | 段ごとに作業を任せるサブエージェント（記録、点検、候補、登録） |
| 台帳 | 回ごとの進み具合の記録（`chosei/ledger.json`） |

図鑑は次の指摘を予測する道具ではない。出た指摘をあとの会話と別のエージェントに引き継ぎ、同じ指摘の繰り返しを防ぐ道具である。そのため取り込みは、作業の途中で指摘が出るたびに行う。指摘を言い換えずに原文で引く理由は 6 節にある。測定の結果は `README.md` にある。

スクリプトのパスは、このスキルのフォルダからの相対で書く。どれも標準ライブラリだけで動く。データの場所は `--home` か環境変数 `SEYO_HOME` で、プロジェクトは `--project` か環境変数 `SEYO_PROJECT` で受け取る。

## 1. 経路の選び方

| 場面 | 経路 |
|---|---|
| 作業の途中で指摘が出て、取り込みを頼まれた | 3 節。対象は進行中の会話 |
| 長い作業や複数のセッションをまとめて取り込む | 4 節。量が多いと、記録の段の照合と点検を通さなければ、条件の落ちを見つけられない。プロジェクトで初めての取り込みなら、検証を行うかを利用者に尋ねる |
| 取り込みの効果を測る | 7 節。採点に使う時期の指摘が一度でも図鑑に入ると、試験が未見でなくなる。その時期は、取り込む前に決める |

## 2. 置き場とプロジェクト

データは `SEYO_HOME`（既定は `~/.seyo/`）の下に置き、作業フォルダには置かない。原文は非公開で、作業ツリーは作業が終わると削除されるからである。

| 場所 | 内容 |
|---|---|
| `projects/<キー>/entries.jsonl` | 控え |
| `projects/<キー>/genten.md` | 図鑑。登録の担当が案を書き、スクリプトが照合して置く |
| `projects/<キー>/project.json` | 作業フォルダの場所の一覧と、引き継ぐプロジェクト |
| `projects/<キー>/chosei/` | 対話の抜き出し、回、台帳、検証 |
| `common/` | 共通の控えと図鑑。利用者が指示した項目だけが入る |

プロジェクトのキーは、次の順に決まる。

1. `--project` か `SEYO_PROJECT`
2. 場所の一覧との一致
3. 作業フォルダの最上位の名前（git の作業ツリーなら、その最上位）

同じ名前で場所の違う作業フォルダでは、スクリプトは決めずに終了する。その場合は、どのプロジェクトかを利用者に尋ね、`scripts/seyo_project.py` の add-path か add で登録する。書く側のスキルは `scripts/seyo_where.py` で、読む図鑑と節の行の範囲を知る。形式と、古い形式の候補の移行は `references/data.md` にある。

## 3. 作業の途中の取り込み

数件の指摘を、利用者の 1 回の依頼で取り込む。担当は候補と登録の 2 つである。反応の分類（承認か、取り下げか）も候補の担当が同時に行うので、条件が落ちる危険は 4 節の経路より大きいと考えられる。この経路は測定していない。

1. 範囲を決める。いまの会話の記録は、記録のフォルダで最も新しく更新された jsonl である。Claude Code の記録のフォルダは `~/.claude/projects/<作業フォルダのパスの英数字以外を - に置き換えた名前>/` にある。
   - `python scripts/extract_dialog.py --list <フォルダ>` が「10 分以内に更新された」と示す記録が複数あれば、利用者のいまの依頼の文で検索して決める。
   - `extract_dialog.py --round <回> <jsonl>` は、取り込み済みの続きから最後の利用者の発言までを範囲にする。範囲の始まりを指定されたら、`--since <日付か時刻>` を付ける。
2. 候補を作り、照合する。担当に `references/brief_candidates.md` の「対話から直接取り出す場合」で範囲の対話を読ませる。依頼文には「対話から直接」と書き、対話のファイルと発言の範囲を添える。`check_candidates.py --round <回> --from-dialogs` の問題を 0 件にさせる。
3. 控えに足す。`install_round.py --round <回>` を実行する。照合を通らない回は足されない。
4. 登録の案を作る。別の担当に `references/brief_register.md` で図鑑の案に足させ、外した候補を一覧にさせる。
5. 案を照合して、利用者に示す。`check_genten.py --round <回>` は、問題が 0 件なら、登録する件と外す件を案として表示する。それを利用者に示し、了承を得る（5 節）。
6. 了承を得たら、`check_genten.py --round <回> --install` で設置し、報告する（5 節）。

## 4. まとめて取り込む経路

記録、点検、入力、候補、照合、控え、登録、案の提示、設置、報告の順に進める。判断の要る段は別の担当に任せ、候補の担当には記録だけを読ませる。条件や限定が落ちる失敗は図鑑からは見分けられないので、段の出力ごとに照合する。判断が要る段には、使える中で最も能力の高いモデルを使う。

担当への依頼文は「指示書 `<このスキルのフォルダ>/references/<指示書>` を読み、そのとおりに作業する」とする。添えるのは、SEYO_HOME、プロジェクトのキー、このスキルのフォルダの絶対パス、回の名前、下の表の値である。回のフォルダは `$SEYO_HOME/projects/<キー>/chosei/rounds/<回>/` である。

| 段 | 指示書 | 添える値 | 出力 |
|---|---|---|---|
| 記録 | `brief_records.md` | 対話のファイル、発言の範囲、出力のファイル | `records/<ID8>_<連番>.jsonl` |
| 点検 | 同じ指示書の 7 節 | 対話のファイル、発言の範囲、点検する記録、点検の出力 | `records/CHECK_<ID8>_<連番>.md` |
| 候補 | `brief_candidates.md` | 入力の番号 | `cand_NN.jsonl` |
| 登録 | `brief_register.md` | なし | `genten.draft.md`、`excluded.jsonl` |

1. 記録。`extract_dialog.py --list` で取り込みの済んでいないセッションを示し、利用者に選んでもらう。`--round <回> <jsonl ...>` で範囲を作る。Codex の記録や貼り付けた対話は、data.md の 2 節の形の md に直せば渡せる。担当はセッションごとに 1 つとし、`scope.json` の `parts` が 2 つ以上なら範囲ごとに分ける。1 つの担当が読む量を抑え、読み落としを減らすためである。`check_records.py --round <回>` の問題を 0 件にさせる。
2. 点検。別の担当に点検させ、結果を取り出した担当に渡す。記録を直させ、取り出されていなかった指摘を加えさせ、照合をやり直す。担当が同意しない件は、このスキルを動かすエージェントが対話を読んで決める。決められなければ、反応を `unknown` にする。
3. 入力。`build_input.py --round <回>` で、7 万字ごとの `in_NN.md` を作る。
4. 候補と照合。担当は入力ごとに 1 つとし、`check_candidates.py --round <回>` の問題を 0 件にさせる。「どの候補の根拠にも使われなかった記録」に落ちた判断があれば、加えさせる。
5. 控え、登録、案の提示、設置、報告は、3 節の 3〜6 と同じである。登録の担当は回ごとに 1 つにする。

## 5. 案の提示、設置、報告

控えへの追加は、利用者の確認を待たずに行う。控えは照合と復元のための全件の記録で、書く側は読まないからである。

図鑑への設置は、案を利用者に示して了承を得てから行う。図鑑は書く側が毎回読むので、何が入るかを利用者が先に確かめられるようにする。案として示すのは、`check_genten.py --round <回>` が表示する二つである。

- 登録する件（見出しと引用の最初の行）
- 外す件（理由つき）

利用者が外す件を入れるよう言えば、`check_genten.py --round <回> --include <id> --heading <主題>` で写しをそのまま足す。主題は、その種類の節にある見出しから合うものを選び、無ければ短い名詞句にする。了承を得たら `--install` で設置する。

`check_genten.py` は、設置の前に次を確かめる。引用が控えの写しと一字も違わないこと、前の版の引用と注が残っていること、回の候補が登録か外した一覧のどちらかにあることである。図鑑は前の版と比べて照合するので、登録は回を 1 つずつ行う。登録を待つ回は `check_genten.py --pending` で分かる。

設置したら、`--install` が最後に表示する共通に移す候補を、id、写し、理由の形で示す。候補が無ければ、候補の欄を出さない。取り消しは `install_round.py --remove <回>` で行い、控えと図鑑からその回を外す。

## 6. 守ること

- 候補と図鑑の案は担当に書かせ、このスキルを動かすエージェントは書かない。このエージェントは対話を読む立場にあり、自分で書くと照合を経ない判断が入る。自分は照合の結果と担当の報告を、目的に照らして読む。
- 写しは一字も変えず、図鑑の引用と注は足すだけにする。言い換えた写しでは、利用者の語と条件が落ちたかを照合できない。引用を書き換えると、前に取り込んだ指摘が失われる。
- 指摘を規則の文に言い換えない。指摘の位置と理由が落ち、読んだ AI が指摘の外まで当てはめる。
- 共通に移すのは、利用者が id を指示した項目だけにする（`common_entries.py add <id>`）。共通の図鑑はすべてのプロジェクトで読まれる。エージェントの判断で移すと、1 つの作業で出た指摘が、利用者の考えていない作業にまで当てはめられる。示す候補も、スクリプトが 2 つの条件（範囲を述べた言い方、別のプロジェクトの近い写し）で挙げたものに限り、印象で足さない。
- 共通の図鑑は、書く側が種類の節を問わず全体を読む（`seyo_where.py --kind` もそう示す）。指摘は元のプロジェクトの種類の節に置かれたまま写される。種類の節だけを読むと、別の種類の文書を書くときに読まれず、共通に移した意味が失われる。利用者が選んだ項目だけが入るので、全体を読んでも分量は小さい。
- 別のプロジェクトを引き継ぐのは、利用者が元のプロジェクトを名指ししたときだけにする（`seyo_project.py inherit <元のキー>`）。別のプロジェクトの指摘は、別の文書と読み手に向けたものである。名前や内容が似ているという推測で引き継ぐと、境界の外の指摘が読まれる。
- 利用者の発言、記録、図鑑を `SEYO_HOME` の外に出さない。担当にも、Web 検索と外部のサービスを使わせない。
- 利用者の取り込みは、その利用者の図鑑だけを変える。層の既定の改訂は、スキルの保守者が行う（`references/maintainer.md`）。
- 途中で止めた場合、どこまで進んだかは回のフォルダのファイルと台帳で分かる。

## 7. 検証

図鑑が、取り込みに使っていない時期の指摘をどれだけ解消し、再現するかを測る。任意で、費用が大きい。手順は `references/kensho.md` にある。
