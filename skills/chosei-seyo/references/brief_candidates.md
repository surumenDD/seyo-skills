# 依頼: 指摘の記録から、判断の候補を取り出す

この指示書は、chosei-seyo の候補の担当が読む。SEYO_HOME、プロジェクトのキー、chosei-seyo のフォルダ、回の名前、入力の番号（2 桁。`in_01.md` なら `01`）は、依頼文の最後に書いてある。以下、`<P>` は `<SEYO_HOME>/projects/<キー>/` を、`<回>` は `<P>/chosei/rounds/<回の名前>/` を、`<スキル>` は依頼文に書いた chosei-seyo のフォルダを、`<番号>` は入力の番号を指す。

## 1. 目的

ある利用者が、AI の書いた文章と AI の振る舞いに出してきた指摘の記録がある。この記録から、利用者のプロジェクトごとの原文の図鑑に足す候補を取り出す。図鑑は、AI が文章を書く前と確認するときに読む文書で、利用者の発言の原文を、文書の種類と主題の見出しの下に改変せずに引いてある。候補はすべて控えに残り、次の段の登録の担当が候補だけを読んで、あなたが写した利用者の発言（user_words）を図鑑にそのまま引き、文書の種類（doc_kind）の節に置く。当てはめすぎを防ぐ注に書けるのは、limits にある境界と経過だけである。

図鑑を読む AI も登録の担当も、記録や対話を読まない。あなたの候補に書かれなかった判断と条件は、図鑑に入らない。取り出すときに判断の条件や限定が落ちると、図鑑を読んだ AI は、利用者が問題にしていない所まで直す。この 2 つの失敗（判断を落とす、条件を落とす）を避けることが、この依頼の中心である。写しは文の途中で切らず、指摘の理由と条件を含む文の単位で写す。図鑑は原文を読ませるものなので、切れた写しでは指摘の位置と理由が伝わらない。

## 2. 読むもの

記録として読むのは `<回>/in_<番号>.md` だけで、全部を読む。ほかに読むのは、この指示書と、出力の形式を書いた `<スキル>/references/data.md` の 6 節だけである。決められた入力だけから候補を作ることで、照合が候補と入力の対応を確認でき、検証を行う場合には、入力から外した時期の指摘で図鑑の効果を測れる。

入力には、2 種類の記録が時刻の順に並んでいる。

- 「## 原稿」: 利用者が、AI の書いた原稿や案を読んで出した発言の全文。続けて、指摘ごとに、対象、対象の本文の冒頭、そのあと AI がしたこと、直したあとの本文の冒頭、そのあとの利用者の反応が並ぶ。
- 「## 進め方」: AI の進め方、返答や報告の書き方、ほかの AI への依頼文のような内部文書に向けた利用者の発言。それより前の指示、AI の応答の抜き出し、起きたことが並ぶ。

利用者の発言は記録のままで、誤字もそのままである。「読んでいたもの」「対象」「そのあと AI がしたこと」「起きたこと」は、記録を整理した別の AI が書いた説明である。

反応の種類は次のとおりである。approved は名指しの承認、approved_blanket は文を名指ししない包括的な承認、re_criticized は直したあとに再び指摘された、withdrawn は利用者が指摘を取り下げた、discarded_later は直した版ごとあとで退けられた（その時期の直し方を利用者が全体として退けている。指摘そのものは有効である）、unknown は記録に無い。「（取り込みに使う範囲の外の発言なので省いた）」は、反応が入力の範囲の外にあることを示す。その経過は分からないものとして扱い、推測で補わない。

## 3. 取り出すもの

入力に現れた利用者の判断を、1 つずつ候補にする。判断とは、利用者が AI の文章や振る舞いの何を問題にしたか、何を良いとしたか、である。

`<回>/cand_<番号>.jsonl` に、1 つの候補を 1 行の JSON で書く。欄の一覧と例は `<スキル>/references/data.md` の 6 節にある。id は `c<番号>-01` から振る。

| 欄 | 書き方 |
|---|---|
| judgment | 利用者の語（利用者が繰り返し使う独自の言い方を含む）を残し、自分の言葉で一般化しすぎない。「分かりやすく書く」のような、どの利用者にも当てはまる言い方にしない。「利用者は〜を問題にしている」「利用者は〜を求めている」の形で書く。図鑑には載らず、登録の担当が何についての指摘かを知るために読む |
| user_words | 利用者の発言から、この判断を表す部分を一字も変えずに写す。1〜4 個、1 つ 300 字以内。文の途中で切らず、理由と条件の文を含める。離れた部分は「（中略）」でつなぐ。AI の文や説明の欄からは写さない |
| ai_pattern | 評価の語を使わない。「返答の冒頭に、依頼の内容を言い直す段落を置いた」のように、入力に書かれた事実から書く |
| applies_to | 何についての指摘か（文書の本文、要約、図の説明、AI の返答、作業の進め方、ほかの AI への依頼文、など。入力から分かる範囲で） |
| doc_kind | 指摘が向いた文書の種類。論文、発表（スライドと台本）、報告（利用者への返答、報告、説明）、査読への回答、メール、AI 向けの文書（指示書、スキルの本体、ほかの AI への依頼文）、付属文書（README など人が読む文書）、一般の読み手への説明、進め方（作業の進め方への指摘）、その他のどれか。2 つにまたがるときは、利用者が問題にした文や振る舞いがある側にする |
| general、general_words | 発言そのものに、範囲を述べた語（「いつも」「どの作業でも」「あなただけの環境ではない」のように、指摘がプロジェクトに限らないと読める語）がある場合だけ、general を true にし、その部分を user_words から一字も変えずに general_words に写す。内容が一般的に見えるという理由では付けない。この印は、利用者に共通の置き場へ移すかを尋ねる候補にだけ使われ、根拠の無い印は、利用者が考えていない作業にまで指摘を広げる提案になる。無ければ false と空の文字列 |
| n_utterances | この判断が現れた、別々の利用者の発言の数。入力の見出しの、セッションと発言の番号で見分け、同じ発言から取り出された原稿の記録と進め方の記録は 1 と数える |
| limits | 最も重要な欄である。利用者は、同じ語を、ある場所では外させ、別の場所では残させることがある。指摘を取り下げることも、AI が指摘を広げすぎたことをあとで指摘することもある。こうした条件と、該当の記録の id を書く。登録の担当は、ここを読んで取り下げられた指摘を外し、図鑑の注を書く。無ければ空にする |
| strength | 強い: 複数の発言で繰り返され、利用者が理由を述べている。弱い: 1 回だけか推量の形で、そのあとの経過が分からない。その間をふつうとする |

## 4. 取り出すときの注意

- 1 つの発言に複数の判断があれば、候補を分ける。別々の発言に同じ判断が現れたら、1 つの候補にまとめて evidence を加え、それぞれの発言の写しを user_words に入れる（4 個まで）。
- 小さな単位の指摘（語を 1 つ外す、など）は、利用者が挙げた理由のほうを判断として取り出す。理由が書かれていなければ、指摘そのものを取り出し、strength を弱いにする。
- その文書だけに固有の決定（特定の図の番号、特定の段落の扱い）は候補にしない。決定の理由が一般の判断を示していれば、理由を候補にする。
- 取り下げられた指摘（withdrawn）は、候補にしないか、取り下げを limits に書いた候補にする。AI が理由を挙げて反論し、利用者が受け入れた出来事は、それ自体を候補にする（利用者が何を訂正として受け入れたか）。
- 承認だけの記録からは、何が承認されたかが入力から分かる場合にだけ候補を作る。「ok」は、内容を把握したという意味のことがある。
- 利用者の指摘を、規則の文（〜すること、〜してはならない）に言い換えない。規則の文は、指摘の位置と理由を落とし、読んだ AI が当てはめすぎる原因になる。
- 入力に現れていない判断を、一般の知識から加えない。

書き終えたら、次を実行して、問題が 0 件になるまで直す。出力の「どの候補の根拠にも使われなかった記録」は、判断を落としていないかを読み直す手がかりにする。根拠にならない記録（作業の依頼に近い発言など）があるのは問題ではない。

```
python <スキル>/scripts/check_candidates.py --round <回の名前> --home <SEYO_HOME> --project <キー> <番号>
```

ファイルは Write ツールで書く。シェルのヒアドキュメントに日本語の JSON を入れると、文字が壊れることがある。

### 対話から直接取り出す場合（作業の途中の取り込み）

依頼文に「対話から直接」とあれば、入力の代わりに、依頼文に書いた対話のファイル（`<P>/chosei/dialogs/<セッション ID>.md`）の、範囲の発言を読む。作業の途中で出た数件の指摘を取り込む経路で、対話は進行中の会話であることが多い。範囲の外の発言は、指摘の前提と経過を確認するためにだけ読む。出力は `<回>/cand_01.jsonl`、id は `c01-01` から振り、evidence は「<ID8> <発言の番号>」（例「aaaa0001 U004」）の形で書く。記録の段を通らないので、記録の担当が受け持つ 2 つの作業も行う。1 つは、指摘がどの文やどの版に向いたものかを、直前の応答で確かめることである。もう 1 つは、指摘のあとの経過（承認、取り下げ、再指摘）を対話から読み、limits に書くことである。範囲が最後の発言で終わり、経過がまだ無い指摘は、経過が分からないものとして扱う。照合は次のとおりである。

```
python <スキル>/scripts/check_candidates.py --round <回の名前> --home <SEYO_HOME> --project <キー> --from-dialogs
```

## 5. してはいけないこと

- 読むのは、入力（対話から直接取り出す場合は範囲の対話）と、この指示書と、data.md と、照合のスクリプトだけにする。ほかのファイル、フォルダ、リポジトリ、図鑑を開かない。
- 書き込むのは `cand_<番号>.jsonl` だけにする。控えへの設置と図鑑への登録は、照合のあとに別の段が行う。
- 記録には、利用者の作業の内容と個人の発言が含まれる。Web 検索と外部のサービスを使わない。環境変数を一覧で表示しない。

## 6. 報告

最後の返答に、次を 300 字以内で書く。

1. 候補の数（strength ごと、doc_kind ごと）と、照合の結果。
2. limits を書いた候補の数と、general を true にした候補の数。
3. 候補にするか迷って落とした判断。
4. この指示書どおりに進めると誤った結果になると考えた点。
