# 依頼: 会話の記録から、利用者の指摘を取り出す

この指示書は、chosei-seyo の 1 段目（記録）の担当が読む。7 節だけは、取り出した記録を点検する別の担当が読む。SEYO_HOME、プロジェクトのキー、chosei-seyo のフォルダ、回の名前、対話のファイルと発言の範囲、出力のファイルは、依頼文の最後に書いてある。以下、`<P>` は `<SEYO_HOME>/projects/<キー>/` を、`<回>` は `<P>/chosei/rounds/<回の名前>/` を、`<スキル>` は依頼文に書いた chosei-seyo のフォルダを指す。

## 1. 目的

利用者が AI の文章と AI の振る舞いに出してきた指摘を、その利用者のプロジェクトごとの原文の図鑑（AI が文章を書く前と確認するときに読む、指摘の原文を引いた文書）に取り込む。この依頼はその 1 段目で、対話の抜き出しから、指摘を記録の形に取り出す。

次の段の担当は記録だけを読み、対話を読まない。記録に入らなかった指摘と、記録で落ちた条件（どの文に向けた指摘か、そのあと承認したか取り下げたか）は、図鑑に入らない。取り出しやすい語句の指摘だけを集めると、段落の組み立て、章の役割、文書全体の方向への指摘が落ち、図鑑が利用者の判断の中心を扱わなくなる。大きな単位の指摘を落とさないことを、最も重く見る。

## 2. 読むもの

- 依頼文に書いた対話のファイル（`<P>/chosei/dialogs/<セッション ID>.md`）の、範囲の発言を全部読む。見出しの番号（U012、Q003、B001）と括弧の中の時刻で範囲を判断する。範囲の外の発言は、指摘の前提になった指示と、指摘のあとの経過を確認するためにだけ読む。
- 記録の形式: `<スキル>/references/data.md` の 2〜4 節。
- 指摘の対象が対話に無いファイル（リポジトリの原稿など）の場合は、そのファイルを読み取りだけで開き、git の履歴（`git log`、`git show`）で対象の版を特定してよい。
- 対話の抜き出しに欠けている発言があると気づいた場合（あとの発言が参照している指示が見当たらない、など）は、もとの jsonl（パスは `<回>/scope.json` のそのセッションの `source`）を読み取りだけで確認し、報告に書く。

## 3. 取り出すもの

出力のファイル（`<回>/records/<ID8>_<連番>.jsonl`）に、原稿の記録と進め方の記録を、1 件 1 行の JSON で書く。範囲の発言だけを対象にし、該当が 0 件なら空のファイルを書く。

### 3.1 原稿の記録（review）

利用者が、AI の書いた原稿や案（文書の本文、対話の中で示した構成案や文案）を読んで出した発言を、1 回の発言につき 1 件とする。発言の中の指摘ごとに `points` に分け、1 つの指摘を、直した箇所ごとに別の指摘に分けない。

- 規模を問わず取り出す。章の役割、章どうしのつながり、文書全体の方向に及ぶ指摘は、語句の指摘より取り出しにくいが、利用者の判断の中心であることが多い。
- 対象がリポジトリの原稿なら、`target.repo` に作業ツリーの絶対パスを、`target.files` に作業ツリーからの相対パスを書く。対象の版は、対話の前後（版の名前、コミットの指示、日付）と git の履歴から特定して `target.commit` に書く。特定できなければ `commit` を空にし、`note` に理由を書く。推測で埋めると、あとで別の版を正解として扱う誤りになる。`commit` が空のとき、照合はいまの作業ツリーのファイルと比べるので、原稿がその後に書き換えられていれば target_text が一致しない。その場合は、対話に写っている本文を写すか、target_text を空にして `note` に書く。版の番号が複数の系統にある場合は、`target.what` に両方を書く。
- 対象が対話の中の案なら、`target.what` を「U012 の直前の応答」の形にし、`target_text` にその案の該当箇所を写す。章や節の全体が対象で長い場合は、本文を `<回>/records/texts/<id>_p<n>_before.md` と `_after.md` に保存し、欄には `texts/<ファイル名>` と書く。
- 図、色、デザインへの指摘は、`scale` を「図・デザイン」とする。
- あとで方向ごと退けられた版への承認は、`user_followup.type` を `discarded_later` にし、退けた発言を `evidence` に写す。利用者が一定の期間の作業全体を退けた場合は、その期間の記録の `era` を「退けられた期間」にする。その期間の承認は、良い文章の根拠として使えないからである。

### 3.2 進め方の記録（scene）

原稿ではないものへの発言を、指摘された AI の応答と組にする。`kind` は次の 5 つである。

| kind | 対象 |
|---|---|
| 進め方への指摘 | AI の作業の進め方。承認の前に編集した、質問に答えずに作業を進めた、指示を読み直さなかった、確認せずに推測で決めた、資料や利用者の言葉をうのみにした、範囲を勝手に広げた、または狭めた、など |
| 返答・報告への指摘 | AI が利用者に向けて書いた返答、報告、提案、説明、質問の文章。何を言っているか分からない、情報が多すぎる、どこを変えたかが見えない、事実と解釈が混ざっている、など |
| 内部文書への指摘 | AI が書いた、原稿ではない文書。ほかの AI への依頼文、規則の文面（CLAUDE.md など）、継続書、決定の記録、調査の報告 |
| 進め方・返答への肯定 | AI の進め方や返答を、利用者が理由を挙げて良いと述べた発言。AI の反論や訂正を受け入れた発言を含む。「ok」「ありがとう」だけの発言は対象にしない |
| 取り下げ・留保 | 利用者が自分の指摘を取り下げた、または留保を付けた発言のうち、進め方と返答にかかわるもの。原稿への指摘の取り下げは、もとの指摘が範囲の中にあれば、その原稿の記録の `user_followup` に書き、範囲の外（前の回）にあれば、ここに記録する |

1 つの発言に、原稿への指摘と進め方への指摘が混ざっている場合は、それぞれの記録に分ける。過去の会話での AI の振る舞いを、あとの発言で振り返って述べている場合（作業を頼む発言の前置きに多い）は、最初の 1 回だけを取り出し、繰り返しは `note` に「同じ指摘の繰り返しが <番号> にある」と書く。同じ指摘を二重に数えると、実際より多く繰り返された指摘に見える。

### 3.3 取り出さないもの

作業の依頼、内容の質問、利用者の新しい構想、範囲を広げる指示は取り出さない。対象の文章を読んでも言えない発言であり、図鑑に入れても、AI が書く文章の判断にならないからである。ただし、依頼の中に AI の文章や進め方への判断（条件、理由、退けた案）が含まれていれば、その部分を取り出す。見出しに重複の印がある発言も取り出さない（別のセッションで記録される）。

迷った件は、落とさずに取り出す。進め方の記録では `confidence` を「低」にし、原稿の記録では `note` に理由を書く。

## 4. 守ること

- 利用者の発言と AI の文は、一字も変えずに写す。誤字もそのまま写す。照合のスクリプトが文字列で比べるからであり、言い換えた写しは、次の段の担当が利用者の語を使えなくする。離れた部分をつなぐときは「（中略）」を挟む。
- 利用者の指摘を、規則の形（〜すること）に言い換えない。解釈を書いてよいのは `scale`、`where`、`after.how`、`what_happened`、`note` だけである。規則に言い換えると、指摘の位置と理由が落ち、図鑑を読んだ AI が指摘の外まで当てはめる。
- 承認は、利用者の発言から特定できる場合にだけ記録する。「ok」は、内容を把握したという意味のことがある。「ok」のあとに質問や指摘が続く場合は、承認として扱わない。文を名指ししない包括的な承認（「よいです。コミットして」）は `approved_blanket` にする。
- 取り下げは `withdrawn` として、その発言と一緒に記録する。取り下げた指摘は、図鑑で「この場合は直さない」という境界になる。
- 記録の date には、見出しの括弧の中の日付（｜のあと）をそのまま写す。
- ファイルは Write ツールで書く。シェルのヒアドキュメントに日本語の JSON を入れると、文字が壊れることがある。
- 書き終えたら、次を実行して、問題が 0 件になるまで直す。

```
python <スキル>/scripts/check_records.py --round <回の名前> --home <SEYO_HOME> --project <キー> <出力のファイル>
```

## 5. してはいけないこと

- 書き込むのは、出力のファイルと `<回>/records/texts/` だけにする。
- 対話、jsonl、リポジトリは読むだけにする。編集、コミット、ブランチの操作、stash をしない。利用者の設定とメモリを変更しない。
- 記録には、利用者の作業の内容と個人の発言が含まれる。Web 検索と外部のサービスを使わない。環境変数を一覧で表示しない（API キーが含まれることがある）。

次の場合は、作業を止めて報告する。対話のファイルが無い。リポジトリの原稿への指摘のうち、対象の版を特定できない件が半分を超える。リポジトリに書き込む必要が生じた。この指示書のとおりに進めると、大きな単位の指摘が落ちると判断した。

## 6. 報告

最後の返答に、次を 400 字以内で書く。

1. 範囲の発言の数、記録の件数（原稿の記録は scale ごと、進め方の記録は kind ごと）、照合の結果。
2. 取り出すか迷って落とした発言の種類と件数。
3. 対象の版を特定できなかった件の数と理由。
4. この指示書どおりに進めると誤った結果になると考えた点。

点検の結果（`CHECK_…md`）を渡されて直すときは、件ごとに対話を読み直し、正しいと判断した点を直し、取り出されていない指摘を加え、照合を通したうえで、同意しない件とその理由を報告する。

## 7. 点検の担当へ

この節は、取り出した担当とは別の担当が読む。照合のスクリプトは写しが正確かを確認するが、指摘がどの文に向けたものか、反応の分類が正しいか、取り出されなかった指摘が無いかは確認できない。この点検はそれを受け持つ。

- 読むもの: 点検する記録のファイル、対話のファイル、この指示書の 3〜5 節、`<スキル>/references/data.md` の 2〜4 節。取り出した担当の報告は読まない。報告を読むと、その判断を追認する点検になるからである。
- 件ごとに判定すること: 指摘が、記録した対象の文や版に向けたものか。反応の分類（承認、包括的な承認、再指摘、取り下げ、退けられた、不明）が、利用者の発言と合うか。対象の版の特定が妥当か。進め方の記録の `what_happened` に評価の語が無いか。
- 記録全体で判定すること: 範囲の発言のうち、取り出されていない指摘（特に章や文書全体の単位の指摘と、取り下げ）が無いか。
- 出力: 依頼文の「点検の出力のファイル」（`<回>/records/CHECK_<ID8>_<連番>.md`）に、食い違った件の id、判定、根拠の発言の番号を書く。取り出されていない指摘は、発言の番号と、どの種類の記録になるかを書く。点検する記録のファイルは書き換えない。直すのは取り出した担当である。この節の担当にとって、5 節の「書き込むのは出力のファイルだけ」の出力のファイルは、点検の出力のファイルを指す。
- 最後の返答に、点検した件数、食い違った件数、取り出されていない指摘の数を 200 字以内で書く。
