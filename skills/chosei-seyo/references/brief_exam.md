# 依頼: 原稿の記録を、検証の試験問題に組み立てる

この指示書は、chosei-seyo の検証で試験問題を組み立てる担当が読む。SEYO_HOME、プロジェクトのキー、chosei-seyo のフォルダ、試験の回の名前、担当する単位の id（原稿の記録の id）は、依頼文の最後に書いてある。以下、`<P>` は `<SEYO_HOME>/projects/<キー>/` を、`<回>` は `<P>/chosei/rounds/<試験の回の名前>/` を、`<単位>` は `<P>/chosei/exam/units/<単位の id>/` を、`<スキル>` は chosei-seyo のフォルダを指す。

## 1. 目的

利用者が AI の文章に出した指摘を、原文の図鑑を渡した別のモデルがどれだけ解消し、再現できるかを測る。試験では、受験するモデルに「利用者がその発言の時点で読んでいたもの」を見せ、書き直させる（書き直し）か、利用者が指摘する問題を挙げさせる（指摘の再現）。あなたが作るのは、受験する側に見せる資料と、採点に使う正解の記録である。材料は、試験の回の原稿の記録で、利用者の 1 回の発言が 1 件の JSON になっている。

結果を左右するのは次の 3 点である。

1. 見せる資料に、答えが漏れていないこと。指摘された箇所だけを抜き出して見せると、問題の場所が分かってしまう。利用者が読んでいたもの全体を見せ、文脈の説明に指摘の内容を書かない。
2. 正解にしてよい指摘だけを正解にすること。利用者は、自分の指摘をうのみにせず、誤っていれば訂正するよう AI に求めることがある。AI の反論を受けて取り下げた指摘や、利用者が残すと決めた箇所を「直すべき問題」にすると、正しく反論する回答が不正解になる。
3. 見せる資料だけでは言えない指摘を、正解にしないこと。

この試験の結果は、図鑑への取り込みには使わない。採点に使う時期の内容が図鑑に入ると、試験が未見でなくなるからである。あなたが読んだ内容を、ほかの文書に書かない。

## 2. 読むもの

1. 担当の単位の記録: `<回>/records/*.jsonl` のうち、id が担当の id の行。欄の意味は `<スキル>/references/data.md` の 3 節にある。review_text（利用者の発言の全文）、target（何を読んでの発言か）、points（指摘ごとに quote、scale、where、target_text、after、user_followup）を使う。
2. 対話の抜き出し: `<P>/chosei/dialogs/<セッション ID>.md`。見出し「## U012（時刻｜日付）」ごとに、直前の AI の応答と利用者の発言がある。担当の単位の前後を、指摘のあとの経過が分かる所まで読む。
3. 対象の本文: `<回>/records/texts/` のファイル（記録の欄に `texts/…` と書いた件だけ）。
4. 原稿のリポジトリ: 記録の `target.repo`。読むだけにする。`git -C <repo> show <commit>:<ファイル>` で当時の版を読める。
5. 同じ回のほかの原稿の記録: 同じ箇所の前後の版を扱う単位（chain）を見つけるために、target と where を読む。

`<回>/scope.json` の範囲の外の発言は、経過を確かめるためにだけ読む。

## 3. 作るもの

担当の単位ごとに `<単位>` を作り、次のファイルを書く。

### exhibit.md（受験する側に見せる本文）

利用者がその発言で読んで、指摘の対象にしたもの全体を、一字も変えずに写す。

- 対象が対話の中の AI の応答（案、提案、説明）なら、その応答の全文。ふつうは発言の直前の応答で、発言がそれより前の応答にも向いているなら、その応答も入れる。
- 対象がリポジトリの原稿なら、その版の、指摘が向いた範囲の全体。文書全体への指摘なら全体。特定の節への指摘なら、その節と、指摘が前後とのつながりに向いている場合は前後の節。版は記録の `target.commit` で、空なら対話と git の履歴で特定する。特定できない単位は作らず、報告に書く。
- 指摘された箇所だけに切り詰めない。迷ったら広く取る。全体は 50,000 字までとする。範囲の外（付録、指摘が向いていない別の版）は入れず、飛ばした所に「（この間 n 行を省略）」と書く。範囲の中の行を長さのために省いた場合だけ、gold.json の exhibit_trimmed を true にし、何を省いたかを note に書く。
- 利用者が描画したスライドや PDF を見ていた場合は、画面の文字のもとになったデータ（見出し、文言、図の説明、台本）を写す。同じファイルの画面に出ない欄は、行を抜かずにそのまま写してよい。図と色は写せないので、本文に「（図）」のような印があれば残す。
- 指摘の答えにあたることを、AI がこの発言より前の応答で自分から述べていても、その応答は入れない。利用者がこの発言で読んだものではないからである。
- 応答の中で、AI がそれより前の利用者の指摘を引用したり言い直したりしている部分は削らない。その時点で利用者が読んでいたものだからである。ただし、この単位の指摘そのもの（この発言より後に書かれたもの）が混ざっていないことを確かめる。

冒頭に出どころを 1 行で書く（例: 「出どころ: U002 の直前の応答（chosei/dialogs/aaaa0001-….md）」）。出どころの行と省略の印のほかに、自分の言葉を足さない。

### context.md（受験する側に見せる文脈）

exhibit を読むのに最低限必要な事実だけを、300 字以内で書く。何の文書か、読み手、作業のどの段階のものか（最初の案、直したあとの第 2 版、など）、exhibit に書かれていない前提（略語、番号の付け方）である。この単位の指摘の内容、指摘を示唆する言い方（「〜に注意して読む」）、利用者がこの発言より後に述べた基準、あなたの評価は書かない。どの単位でも同じ調子の、事実だけの文にする。

### fixed.md（固定の資料。要る単位だけ）

exhibit と context だけでは言えないが、決まった資料があれば言える指摘がある場合に、その資料を写す。前の版の同じ箇所（「もとの版にはこの意味があった」という指摘）、用語の一覧、節の順などである。出どころを 1 行ずつ書き、本文は一字も変えずに写す。

### gold.json（正解の記録。受験する側には見せない）

例は架空の会話（町内会の防災訓練のお知らせ）から作った。

```
{"unit": "review-aaaa0001-U002-1", "round": "<試験の回の名前>", "session": "aaaa0001", "turn": "U002", "date": "2026-05-25",
 "exhibit_sources": [{"what": "U002 の直前の応答", "dialog": "chosei/dialogs/aaaa0001-….md", "lines": "40〜52"}],
 "exhibit_chars": 160, "exhibit_trimmed": false,
 "rewrite_ok": true, "rewrite_note": "お知らせの案で、書き直しの対象になる",
 "chain": ["review-aaaa0001-U003-1"],
 "points": [
  {"id": "review-aaaa0001-U002-1#p1",
   "quote": "「本年も防災訓練を行います」は、見出しと同じことを言っているので要らない。",
   "where": "二文目",
   "status": "確定",
   "status_evidence": "AI はその文を除いた（U003 の直前の応答）。利用者はあとで覆していない。",
   "derivable": "本文から言える",
   "derivable_reason": "見出しと二文目が同じことを述べているのは、本文から分かる。",
   "in_exhibit": "本年も防災訓練を行います。",
   "keep_span": ""},
  {"id": "review-aaaa0001-U002-1#p2",
   "quote": "雨天の扱いは、そのままでいい。",
   "where": "最後の文",
   "status": "残す",
   "status_evidence": "利用者が「雨天の扱いは、そのままでいい。」と述べた（U002）。",
   "derivable": "本文から言える",
   "derivable_reason": "保つべき箇所が本文にある。",
   "in_exhibit": "雨天の場合は、体育館で行います。",
   "keep_span": "雨天の場合は、体育館で行います。"}],
 "note": ""}
```

| 欄 | 書き方 |
|---|---|
| unit、round、session、turn、date | 単位の id、試験の回の名前、記録の session（ID8）、turn、date |
| exhibit_sources | 写したもとごとに 1 つ。対話なら what、dialog（プロジェクトのフォルダ `<P>` からの相対パス）、lines。リポジトリの版なら what、repo、commit、file（作業ツリーからの相対パス）。照合が、exhibit の行を対話と git の版で探す |
| exhibit_chars | exhibit.md の字数 |
| rewrite_ok | exhibit が書き直せる文章（原稿、文言、構成の案）なら true。選択肢の一覧や質問への説明のように、書き直しても意味がないものは false |
| chain | 同じ箇所の前後の版を扱う、この回のほかの単位の id。無ければ空の配列 |
| points | 記録の points と 1 対 1。id は「<単位の id>#p<n>」、quote と where は記録のまま写す |
| in_exhibit | 指摘が向いた箇所の、exhibit からそのまま写した短い句。文書全体への指摘なら空 |
| keep_span | status が反論が通った、残すの件で、書き直しで保たれるべき箇所（exhibit から写す）。ほかは空 |

## 4. 分類の決め方

status は、言葉づかいではなく、指摘のあとの経過で決める。利用者は確かな指摘にも推量の形を使うことがあるので、推量の形であることを理由に保留にしない。記録の user_followup は手がかりにし、対話を読んで決める。

- 確定: AI がその指摘を問題として認め（直した、または直すと答えた）、利用者がその認識をあとで覆していない。直した版への利用者の反応が無くても確定である。直し方だけが再び指摘された場合（問題の認識は変わらず、直し方が足りなかった）も確定である。直した版ごと、あとで方向を退けられた場合（discarded_later）も、指摘そのものの認識が覆っていなければ確定である。
- 反論が通った: AI が理由を挙げて、直さない、または別の形にすると答え、利用者が受け入れた。利用者が自分で取り下げた場合（勘違いだった、など）も入れる。利用者が問題の場所を言い直しただけの場合は、取り下げではない。
- 残す: 利用者が、意図がある、必要だ、として残すと決めた。
- 保留: 上のどれでもない。AI が応えていない。AI が直さず、利用者の反応も無い。利用者が保留にした。あとの時期に利用者の判断の向きが変わった。

利用者があとの発言で基準そのものを言い直した場合は、問題の認識が変わっていなければ確定にし、言い直しを note に書く。

derivable は次のとおりである。status と derivable は、単位ではなく指摘ごとに決める。1 回の発言に、文章への指摘と作業の依頼が混ざっていることは多い。

- 本文から言える: exhibit と context を読んだ人が、その箇所の、その性質の問題を指摘できる。利用者と同じ言葉である必要はない。
- 固定の知識が要る: fixed.md に写した資料があれば言える。
- 測れない: 改稿や作業の依頼、利用者の新しい構想や好み、範囲を広げる指示、内容の質問、当日の運用の決定、図や色を見ないと言えないもの、進め方への指摘、exhibit に写せないもの（コード、画像）への指摘。

迷った件は、慎重な側にする。確定か保留かで迷えば保留、本文から言えるか測れないかで迷えば測れないにして、理由を note に書く。測れる指摘が 1 件も無い単位も、ファイルは同じように作る。

## 5. 守ること

- exhibit と fixed は、対話の抜き出しか git の版から、一字も変えずに写す。記憶で書かない。exhibit.md と fixed.md は、対話の行の範囲や git の版を Python で写してよい。スクリプトは `<単位>` の外の一時フォルダに置いて実行する。
- gold.json と context.md は Write ツールで書く。シェルのヒアドキュメントに日本語を入れると、文字が壊れることがある。
- 書き終えたら次を実行し、問題が 0 件になるまで直す。

```
python <スキル>/scripts/check_exam.py --home <SEYO_HOME> --project <キー> <単位の id> [<単位の id> ...]
```

## 6. してはいけないこと

- 書き込むのは、担当の `<単位>` の中と、作業用の一時フォルダだけにする。
- 対話、記録、リポジトリは読むだけにする。図鑑（`<SEYO_HOME>` の下の `genten.md`）、控え（`entries.jsonl`）、取り込みの回のファイルは読まない。正解を決めるのに要らず、読むと図鑑の語で正解を書きやすくなるからである。
- 資料には利用者の作業の内容と個人の発言が含まれる。Web 検索と外部のサービスを使わない。環境変数を一覧で表示しない。

## 7. 報告

最後の返答に、次を 400 字以内で書く。

1. 単位の数、指摘の数、status ごと、derivable ごとの件数、照合の結果。
2. exhibit の決め方で迷った単位と、その決め方。作らなかった単位とその理由。
3. 正解にしなかった件の主な理由。
4. この指示書どおりに進めると誤った結果になると考えた点。
