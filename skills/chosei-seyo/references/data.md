# データの置き場と形式

chosei-seyo のスクリプトと担当が読み書きするファイルの一覧である。例はすべて、町内会の清掃のお知らせを AI に書かせた架空の会話から作ったもので、`scripts/selftest.py` の試験の材料と同じである。

## 1. 置き場とプロジェクト

`SEYO_HOME` は、スクリプトの `--home`、環境変数 `SEYO_HOME`、`~/.seyo` の順に決まる。

```
$SEYO_HOME/
  common/
    entries.jsonl                 共通の控え。利用者が指示した項目だけ（8 節）
    genten.md                     共通の図鑑
  projects/<キー>/
    project.json                  キー、作業フォルダの場所の一覧、引き継ぐプロジェクトの一覧
    entries.jsonl                 控え（8 節）。取り出した指摘の全部で、照合と復元に使う。書く側は読まない
    genten.md                     図鑑（8 節）。登録の担当が書き、check_genten.py が照合して置く
    chosei/
      ledger.json                 設置した回、登録を待つ回、取り込み済みの範囲（7 節）
      dialogs/<セッション ID>.md   対話の抜き出し（2 節）
      rounds/<回>/
        scope.json                回の範囲（7 節。extract_dialog.py --round が書く）
        records/<ID8>_<連番>.jsonl 記録。原稿の記録（3 節）と進め方の記録（4 節）を同じファイルに書く
        records/texts/            長い対象の本文
        records/CHECK_<ID8>_<連番>.md 点検の結果
        in_NN.md、manifest.json   候補の取り出しの入力（5 節）と、その一覧（build_input.py が書く）
        cand_NN.jsonl             候補（6 節）
        genten.draft.md           図鑑の案（8 節。check_genten.py --start が写しを作り、登録の担当が足す）
        excluded.jsonl            登録の担当が外した候補と理由（8 節）
        genten.before.md          図鑑を置く前の版（check_genten.py --install が残す）
      exam/units/<単位の id>/      検証の試験問題（形式は brief_exam.md）
      exam/runs/<測定>/            測定の仕様、計画、回答、採点、集計（形式は kensho.md）
```

置き場を作業フォルダの中に置かないのは、原文が非公開で、リポジトリに入ると公開される危険があり、作業ツリーは作業が終わると削除されるからである。ID8 はセッション ID の先頭 8 文字で、記録の id と、発言の参照（「aaaa0001 U002」）に使う。`dialogs/` は同じプロジェクトの回で共有し、同じセッションを抜き出し直すと上書きする。回の範囲に入った発言の番号は、会話の続きが加わっても変わらないので（2 節）、前の回の記録からの参照は保たれる。

プロジェクトのキーは、どのスクリプトでも次の順に決まる。

1. `--project <キー>`
2. 環境変数 `SEYO_PROJECT`
3. 作業フォルダの最上位が、ある `project.json` の `paths` に登録されていれば、そのキー
4. 作業フォルダの最上位の名前（空白と `\ / : * ? " < > |` は `_` に置き換える）

作業フォルダは `--cwd` で指定でき、既定はいまのフォルダである。最上位は、git の作業ツリーの中ならその作業ツリーの最上位（`git rev-parse --show-toplevel`）、そうでなければ作業フォルダそのものである。4 で決めたキーの `project.json` に別の場所が登録されていれば、同じ名前で場所の違う作業フォルダなので、スクリプトは決めずに終了し、`--project` の指定を求める。そのフォルダが同じプロジェクトなら `seyo_project.py add-path <キー> <フォルダ>`、別のプロジェクトなら `seyo_project.py add <新しいキー> --path <フォルダ>` で登録すると、次からは 3 で決まる。4 で決めたキーは、最初に書き込むスクリプト（`extract_dialog.py --round` など）が `project.json` を作り、場所を登録する。1 か 2 で決めた場合は場所を登録しない。

```
{"key": "demo", "paths": ["/home/user/work/notices"], "inherits": ["paper"]}
```

`inherits` は、このプロジェクトが図鑑を引き継ぐプロジェクトで、利用者が元のプロジェクトを名指ししたときにだけ `seyo_project.py inherit <元のキー>` で加える（`uninherit` で外す）。引き継ぎは 1 段で、引き継いだプロジェクトがさらに引き継ぐものは読まない。

| スクリプト | 内容 |
|---|---|
| `seyo_project.py list` | プロジェクトごとの控えの項目の数、登録を待つ回の数、図鑑の字数、場所、引き継ぎ |
| `seyo_project.py current` | 作業フォルダから決まるキーと、その決め方 |
| `seyo_project.py add`、`add-path`、`remove-path` | 新規の登録、場所の追加と削除。1 つの場所は 1 つのプロジェクトにだけ登録できる |
| `seyo_project.py inherit`、`uninherit` | 引き継ぐプロジェクトの指定と解除 |
| `seyo_where.py [--kind <種類>]` | 読む図鑑を読む順に表示する（8 節） |

## 2. 対話の抜き出し

`extract_dialog.py` が Claude Code のセッションの記録（jsonl）から作る md で、利用者の発言ごとに、その直前の AI の応答の本文を添える。ツールの入出力、思考、システムの注記、スキルの本文、サブエージェントの対話は含まない。

```
## U002（2026-05-20T01:05:00｜2026-05-20）

### 直前の応答

直しました。（AI の応答の本文）

### ユーザーの発言

冒頭のあいさつが長くて、いつ何をするのかが最後まで分からない。日時と場所を最初に書いてほしい。
```

見出しの括弧の中は、時刻（UTC）と現地の日付である。現地の時間帯は、既定ではこの PC の時間帯で、`--tz +09:00` の形で指定できる。記録の date 欄には、この日付をそのまま写す。

| 番号 | 発言 |
|---|---|
| U | 通常の発言。スキルなどを引数つきで呼んだ発言は「/名前 引数」の形で入る。設定のコマンド（/model など）は入らない |
| Q | AI の作業中に届いた発言。同じ文がそのあと U として届いた場合は Q を出さない。作業の途中で受け取られた印のある Q は、あとで同じ文の U が来ても残す |
| B | /btw で届いた発言 |
| E | 最後の発言のあとに残った応答。利用者の発言は無い |

U と Q の番号は、B と E の有無で変わらない。進行中の会話では、最後の U より後の Q がまだ U として届いておらず、届くと Q が消えて、それより後の Q の番号がずれる。届いた U は時刻が遅いので、範囲を時刻で決めると次の回にも入る。そこで `extract_dialog.py --round` は、記録が 10 分以内に更新されたセッションを進行中とみなし、範囲を最後の U までにする。最後の U より前の Q は、すでに U として届いたか作業の途中で受け取られたかが決まっているので、番号は変わらない。例外は、作業の途中で受け取られた印も、同じ文の U も無い Q で、あとで同じ文の U が来ると消える。最後の U より後の発言は、次の回の範囲に入る。

同じプロジェクトの別のセッションに同じ時刻と本文の発言がある場合（会話を分岐させた記録など）は、見出しの末尾に「（重複: aaaa0001 U001 と同じ発言）」と書く。印のある発言は回の範囲に入らず、記録にもしない。同じ発言を二重に数えると、同じ指摘が実際より多く繰り返されたように見えるからである。

Codex の記録や貼り付けた対話は、この形の md に直せば、`extract_dialog.py --round` に jsonl の代わりに渡せる。ファイル名を `<セッション ID>.md` とし（ID の先頭 8 文字は英数字と . _ - で書き、ほかのセッションと重ならないようにする。記録の id と発言の参照にその 8 文字を使うからである）、見出しの日付は省いてよい（時刻から補う）。直すときは、利用者の発言と AI の応答を一字も変えない。

## 3. 原稿の記録

利用者が、AI の書いた原稿や案（文書の本文、対話の中で示した構成案や文案）を読んで出した 1 回の発言を 1 件とし、発言の中の指摘ごとに `points` に分ける。1 件を 1 行の JSON で書く。次の例は読みやすさのために改行してある。

```
{"id": "review-aaaa0001-U002-1", "session": "aaaa0001", "turn": "U002", "date": "2026-05-20",
 "target": {"what": "U002 の直前の応答（お知らせの案）", "repo": "", "commit": "", "files": []},
 "review_text": "冒頭のあいさつが長くて、いつ何をするのかが最後まで分からない。日時と場所を最初に書いてほしい。",
 "points": [{"n": 1, "quote": "冒頭のあいさつが長くて、いつ何をするのかが最後まで分からない。",
             "scale": "段落", "where": "お知らせの冒頭",
             "target_text": "皆さま、いつも町内の美化にご協力いただき、誠にありがとうございます。さて、このたび清掃活動を実施する運びとなりました。",
             "after": {"commit": "", "text_or_path": "texts/review-aaaa0001-U002-1_p1_after.md",
                       "how": "日時と場所を冒頭の文に移し、あいさつの文を除いた。"},
             "user_followup": {"type": "approved", "turn": "U003", "evidence": "ok 承認します"}}],
 "era": "通常", "note": ""}
```

| 欄 | 内容 |
|---|---|
| id | `review-<ID8>-<発言の番号>-<連番>`。連番はふつう 1 で、同じ発言で別々の原稿を読んでいた場合に 2 以上にする |
| session、turn、date | ID8、発言の番号（U012、Q003、B001）、見出しの現地の日付 |
| target | what は何を読んでいたか（対話の中の案なら「U012 の直前の応答」）。リポジトリの原稿なら、repo は作業ツリーの絶対パス、files は作業ツリーからの相対パス、commit はその版。版が分からなければ commit を空にして note に理由を書く。対話の中の案なら 3 つとも空にする |
| review_text | 発言の全文の写し |
| points[].quote | review_text のうち、この指摘にあたる部分の写し |
| points[].scale | 語句、文、段落、章・節、文書全体、図・デザインのどれか。複数なら「／」でつなぐ |
| points[].where | 対象の位置（章、節、段落、文） |
| points[].target_text | 対象の本文の写し。長ければ `records/texts/<id>_p<n>_before.md` に保存し、欄には `texts/<ファイル名>` と書く |
| points[].after | 指摘のあとの版。text_or_path は本文の写しか `texts/<id>_p<n>_after.md`、how は何が変わったかを事実として 1〜2 文（評価を書かない）、commit はリポジトリの版 |
| points[].user_followup | そのあとの利用者の反応。type（下の表）、turn（別のセッションなら「<ID8> <番号>」）、evidence（反応の発言の写し。unknown 以外では必須） |
| era | 通常、または退けられた期間（利用者があとで、その期間の作業を方向ごと退けた）。その期間の承認は、良い文章の根拠にならない |
| note | 不確かな点 |

| user_followup.type | 意味 |
|---|---|
| approved | 名指しの承認 |
| approved_blanket | 文を名指ししない包括的な承認 |
| re_criticized | 直したあとに再び指摘された |
| withdrawn | 利用者が指摘を取り下げた |
| discarded_later | 直した版ごと、あとで退けられた。指摘そのものは有効である |
| unknown | 記録から分からない |

`check_records.py` は、写しの欄が発言や対話に一字一句あるか（空白は問わず、「（中略）」で離れた部分をつなぐ）、target_text と after の 8 字を超える行が対話か target のファイル（commit があればその版を git show で、空ならいまの作業ツリーのファイルを読み、注意を出す）にあるか、反応が指摘より後の発言か、発言が回の範囲の中にあるかを確認する。

## 4. 進め方の記録

AI の作業の進め方、利用者への返答や報告の文章、ほかの AI への依頼文や規則の文面のような内部文書に向けた発言と、その逆向きの発言（理由を挙げた肯定、取り下げ）を、指摘された AI の応答と組にする。1 つの発言に別々の指摘があれば、件を分ける。

```
{"id": "scene-aaaa0001-U004-2", "session": "aaaa0001", "turn": "U004", "date": "2026-05-21",
 "kind": "進め方への指摘", "critique": "それと、どの作業でも、編集する前に案を見せてほしい。勝手に直さないで。",
 "ai_response": {"turn": "U004", "excerpt": "箇条書きにする案です。"},
 "what_happened": "AI は、案を示す前に、お知らせの本文を箇条書きに書き換えた。",
 "prior_instructions": [], "from_response_alone": "いいえ", "confidence": "中", "note": ""}
```

| 欄 | 内容 |
|---|---|
| id | `scene-<ID8>-<発言の番号>-<連番>` |
| kind | 進め方への指摘、返答・報告への指摘、内部文書への指摘、進め方・返答への肯定、取り下げ・留保のどれか |
| critique | 発言のうち、この指摘にあたる部分の写し。範囲を述べた語（「どの作業でも」など）があれば、それも含めて写す |
| ai_response | turn は対象の応答を「直前の応答」に持つ発言の番号、excerpt は対象の部分の写し（800 字以内。長ければ「（中略）」でつなぐ）、session は別のセッションの応答の場合のその ID8 |
| what_happened | AI が何をしたかを事実として 1〜2 文。評価の語を使わない |
| prior_instructions | 指摘が、それより前の指示に反したことを言っている場合の、その指示（turn と quote。別のセッションなら session）。無ければ空の配列 |
| from_response_alone | 指摘の対象が excerpt を読めば分かるか（はい、一部、いいえ）。道具の操作や読まなかった文書への指摘は「いいえ」 |
| confidence | 高、中、低。迷って取り出した件は低にし、note に理由を書く |
| note | 200 字以内 |

## 5. 候補の取り出しの入力

`build_input.py` が回の記録から作る。記録を時刻の順に並べ、1 ファイルが 7 万字を超えないように分ける。

```
## 原稿 review-aaaa0001-U002-1｜aaaa0001 U002 2026-05-20｜通常
読んでいたもの: U002 の直前の応答（お知らせの案）

利用者の発言（全文）:

冒頭のあいさつが長くて、いつ何をするのかが最後まで分からない。日時と場所を最初に書いてほしい。

- 指摘 p1（段落）対象: お知らせの冒頭
  - 対象の本文（冒頭）: 皆さま、いつも町内の美化にご協力いただき、……
  - そのあと AI がしたこと: 日時と場所を冒頭の文に移し、あいさつの文を除いた。
  - 直したあとの本文（冒頭）: 6 月 1 日 9 時から、公民館前に集合して町内の清掃を行います。……
  - そのあとの利用者の反応: approved U003「ok 承認します」

## 進め方 scene-aaaa0001-U004-2｜aaaa0001 U004 2026-05-21｜進め方への指摘
- それより前の利用者の指示: なし
- AI の応答（抜き出し）: 箇条書きにする案です。
- 起きたこと: AI は、案を示す前に、お知らせの本文を箇条書きに書き換えた。
- 利用者の発言: それと、どの作業でも、編集する前に案を見せてほしい。勝手に直さないで。
```

記録の担当の注記（note）と確信度は入れない。候補の担当が、記録の担当の解釈を判断の材料にしないようにするためである。反応の発言が回の範囲の終わりより後にある場合（検証のために範囲を区切った場合だけ起きる）は、反応を「（取り込みに使う範囲の外の発言なので省いた）」に置き換え、その反応を受けた直したあとの本文も入れない。

## 6. 候補

1 つの判断を 1 行の JSON で書く。書き方の注意は `brief_candidates.md` にある。候補はすべて控えの項目になり、登録の担当が図鑑に引くのは user_words だけである（limits は注の材料になる）。

```
{"id": "c01-03", "judgment": "利用者は、案を見せる前に AI が本文を書き換えたことを問題にしている。",
 "user_words": ["どの作業でも、編集する前に案を見せてほしい"], "ai_pattern": "案を示す前に本文を書き換えた。",
 "applies_to": "作業の進め方", "doc_kind": "進め方", "general": true, "general_words": "どの作業でも",
 "evidence": ["scene-aaaa0001-U004-2"], "n_utterances": 1, "limits": "", "strength": "強い", "note": ""}
```

| 欄 | 内容 |
|---|---|
| id | `c<入力の番号>-<連番>`。対話から直接取り出す場合（作業の途中の取り込み）は `c01-<連番>` |
| judgment | 利用者が何を問題にし、何を求めているか。1〜3 文。図鑑には載らず、登録の担当と保守者が読む |
| user_words | 利用者の発言の写し。1〜4 個、1 つ 300 字以内（「（中略）」は数えない）。文の途中で切らず、指摘の理由と条件を含む文の単位で写す |
| ai_pattern | 指摘を受けた AI の文章や振る舞いの形。1〜2 文 |
| applies_to | 何についての指摘か（お知らせの文、作業の進め方、ほかの AI への依頼文、など）。自由な記述 |
| doc_kind | 図鑑の節。論文、発表、報告、査読への回答、メール、AI 向けの文書、付属文書、一般の読み手への説明（層の種類の名前）、進め方、その他のどれか |
| general | 発言そのものが、プロジェクトに限らない言い方になっているか。範囲を述べた語（「いつも」「どの作業でも」「あなただけの環境ではない」など）がある場合だけ true にする。内容が一般的に見えるという理由では付けない |
| general_words | general が true のとき、そう読める部分の写し。user_words のどれかの中にある必要がある。false なら空 |
| evidence | 根拠の記録の id（原稿の記録は `review-…#p1` の形）。対話から直接取り出す場合は「<ID8> <発言の番号>」 |
| n_utterances | 判断が現れた別々の発言の数 |
| limits | 当てはまらない場合、利用者が付けた限定、取り下げ、逆向きの発言と、その記録の id。無ければ空。図鑑の注に書けるのは、ここにある境界と経過だけである |
| strength | 強い、ふつう、弱い |
| note | 任意 |

`check_candidates.py` は、欄と値に加えて、user_words が入力のうち利用者の発言の部分（発言の全文、反応、それより前の指示）にあるかを確認する。AI の文や説明の欄にしか無い文は、利用者の語として通さない。general_words が user_words の中にあるかも確認する。

## 7. 回を管理するファイル

| ファイル | 内容 |
|---|---|
| `scope.json` | 回の範囲。プロジェクトのキー（`project`）、回の用途（`purpose`。取り込みは `intake`、検証の試験は `exam`、古い形式の候補の移行は `migrate`。移行の回はセッションを持たず、元のファイル `sources` を持つ）と、セッションごとに、対話のファイル、もとの記録のパス（`source`）、範囲の始まり（`start_after`。このプロジェクトで前の回までに取り込んだ最後の発言の時刻）、終わり（`end`）、最初と最後の発言の番号、発言と字数、分割の目安（`parts`。どのセッションにも 1 つ以上あり、2 つ以上なら担当を分ける）、進行中とみなしたか（`live`）と次の回に回した発言の数（`deferred`）、`--since` で外した発言の数（`before_since`）と、照合に使う `--since` の下限（`since_from`。この時刻の発言から範囲に入る。`--since` が無ければ空。欄が無い古い回は `since` と時間帯から求める）。始まりや終わりを指定した場合は `since`、`until`、`until_turn` |
| `manifest.json` | 入力のファイルごとの字数と記録の id、記録の数、範囲の外として省いた反応の数 |
| `ledger.json` | 控えに足した回の一覧（`rounds`）。回ごとに、名前、種類（取り込み、移行）、設置の時刻、足した項目の数、図鑑への登録（`genten`。`未登録` か `登録済み`）、登録した候補と外した候補の数、セッションごとの範囲。セッションの取り込み済みの範囲は、設置した回の `end` の最大で決まる。`--since` で外した発言も、それより後の回を設置すると取り込み済みとして扱われる。試験の回（`purpose` が `exam`）は設置できないので、ここに入らない。移行の回はセッションの範囲を持たない |

設置を取り消すには `install_round.py --remove <回>` を実行する。控えからその回の項目を外し、図鑑からその回の引用と注を外し（空になった見出しも外し、外す前の版を回のフォルダに残す）、`ledger.json` から回を消す。その範囲の発言は取り込み済みでなくなり、次の回の範囲に入る。共通に写した項目は残るので、外すなら `common_entries.py remove` を使う。

## 8. 控えと図鑑

控え（`entries.jsonl`）の 1 行は、照合を通った候補 1 つである。設置（`install_round.py`）と移行（`migrate_legacy.py`）が足し、エージェントは直接書かない。文章を書くエージェントは読まない。

| 欄 | 内容 |
|---|---|
| id | `<回>:<候補の id>`（共通では `<元のキー>/<回>:<候補の id>`） |
| round、source_id | 回の名前と、回の中の候補の id |
| time、date | 根拠の発言のうち最も早いものの時刻（UTC）と現地の日付。対話で引けなければ空 |
| 候補の欄 | doc_kind、applies_to、user_words、general、general_words、ai_pattern、limits、judgment、evidence、n_utterances、strength、note |
| installed_at | 足した時刻 |
| origin | 共通の項目だけ。元のプロジェクトと id |
| migrated_from | 移行した項目だけ。元のファイルの名前 |

図鑑（`genten.md`）は、登録の担当（`brief_register.md`）が、回の候補から残す価値のある原文を選んで引いたものである。

```
# 原文の図鑑（プロジェクト demo）

読み方

- （決まった文面。引用は例であり規則ではないこと、注の境界を合わせて読むこと、見出しの分類は AI の整理であること）

## 進め方

### 編集の前の確認

> どの作業でも、編集する前に案を見せてほしい
<!-- r1:c01-03 -->

### 頼まれた範囲

> 頼んだ範囲で直して
<!-- r2:c01-01 -->
（注: 雨天の扱いの文を足す依頼で、連絡方法までは頼まれていなかった。）
```

- 第 2 階層の見出しは文書の種類（候補の doc_kind の値）、第 3 階層の見出しは主題（40 字以内の名詞句。分類は担当の整理）である。
- 引用は控えの項目の user_words の 1 つをそのまま写したもので、すぐ次の行に、その項目の id を HTML のコメントで書く。
- 注（「（注: …）」）は、当てはめすぎを防ぐのに要る場合だけ id の次の行に 1 行で置き、書けるのは項目の limits にある境界と経過だけである。
- 引用、id、注は足すだけで、変更も削除もしない。外せるのは、回の取り消し（`install_round.py --remove`）と、共通から外すとき（`common_entries.py remove`）のスクリプトだけである。
- 登録の担当が外す候補の理由は、返事だけの発言、その文書だけの決定、取り下げられた指摘、既に同じ原文が図鑑にある、の 4 つに限る。外した候補は `excluded.jsonl` に `{"id": "<回>:<候補の id>", "reason": "<理由>", "note": ""}` の形で書く。

`check_genten.py` の働きは次のとおりである。

| コマンド | 内容 |
|---|---|
| `--round <回> --start` | 回のフォルダに案（`genten.draft.md`）を、いまの図鑑の写しで作る。図鑑が無ければ、読み方だけのひな形にする |
| `--round <回>` | 案と外した一覧を照合する。引用が、直後の id が指す控えの項目の user_words のどれかと一字も違わない（行末の空白は問わない）。id が控えにある。引用が種類と主題の見出しの下にあり、種類が項目の doc_kind と同じ。前の版（いまの図鑑）の引用、id、注が、同じ見出しの下に残っている。この回の候補が、登録か外した一覧のどちらか一方にある。外した理由が 4 つのどれか。足した引用の id がこの回の候補である。注は limits のある項目にだけある。主題の見出しが規則や文の形でない。読み方の決まった文面がある |
| `--round <回> --install` | 照合の問題が 0 件なら、案を図鑑として置き、前の版を回のフォルダに `genten.before.md` として残し、台帳の回を `登録済み` にする。登録した件（種類、主題、引用の最初の行、id）、外した件（id、理由、写しの最初の行）、この回の共通に移す候補を表示する |
| `--round <回> --include <id> ... --heading <主題>` | 外した一覧の候補を名指しで登録する。写しを機械的に、その種類の節の主題の見出しの下に置き（無ければ作る）、照合して置き、外した一覧から除く |
| `--pending` | 登録を待つ回（台帳で `未登録` の回）を並べる |
| `--common` | 共通の図鑑を、共通の控えと照合する |

図鑑は前の版と比べて照合するので、登録は回を 1 つずつ行う。2 つの回の案を同時に作ると、あとから置く案に先の回の引用が無く、「前の版の引用が消えた」として断られる。

`seyo_where.py` は、読む順（共通、引き継ぐプロジェクト、いまのプロジェクト）に、存在する図鑑のパス、字数、読み方の行、文書の種類の節（第 2 階層の見出し）ごとの引用の数と字数と行の範囲を 1 行ずつ表示する。`--kind <種類>` を付けると、引き継ぐプロジェクトといまのプロジェクトの図鑑は、その種類の節と「進め方」の節だけを示し、共通の図鑑は、節ごとの内訳の代わりに、全体を読むことと字数と引用の数を示す。共通の図鑑には利用者が指示した指摘だけが元のプロジェクトでの種類の節に置かれたまま写されるので、種類の節だけを読むと別の種類の文書を書くときに読まれず、共通に移した意味が失われる。利用者が選んだ項目だけなので、全体を読んでも分量は小さい。読み方の決まった文面（「書く文書の種類の節と「進め方」の節を読む」）は既存の図鑑の照合に使うので変えず、新しく作る共通の図鑑の共通の行にだけ「種類の節を問わず全体を読む」を足した（この行は照合しないので、既に置かれた共通の図鑑も照合を通る）。図鑑が 1 つも無ければ、そのことを 1 行で示して正常に終わる。プロジェクトを決められない場合は、共通の図鑑だけを示して終了コード 2 で終わる。

```
図鑑を読む順（プロジェクト demo、決め方: 場所の一覧）。各図鑑の読み方と、書く文書の種類の節と「進め方」の節を読む。共通の図鑑は節を問わず全体を読む
1. 共通: /home/user/.seyo/common/genten.md 計 431 字｜読み方 行 1〜10｜進め方 引用 1 72 字 行 11〜16
2. 引き継ぎ paper: /home/user/.seyo/projects/paper/genten.md 計 610 字｜読み方 行 1〜9｜論文 引用 2 160 字 行 10〜21
3. いまのプロジェクト demo: /home/user/.seyo/projects/demo/genten.md 計 642 字｜読み方 行 1〜9｜一般の読み手への説明 引用 3 175 字 行 10〜26｜進め方 引用 2 145 字 行 27〜38
```

`--kind 論文` を付けたときの表示は次のとおりである（1 行目は上と同じ）。

```
1. 共通: /home/user/.seyo/common/genten.md 計 431 字｜全体を読む 引用 1
2. 引き継ぎ paper: /home/user/.seyo/projects/paper/genten.md 計 610 字｜読み方 行 1〜9｜論文 引用 2 160 字 行 10〜21｜進め方 の節なし
3. いまのプロジェクト demo: /home/user/.seyo/projects/demo/genten.md 計 642 字｜読み方 行 1〜9｜進め方 引用 2 145 字 行 27〜38｜論文 の節なし
```

共通の置き場（`common/`）には、利用者が指示した項目だけを `common_entries.py add <id>` で写す。控えの項目を共通の控えに写し（id は `<キー>/<id>`）、プロジェクトの図鑑からその id の引用と注を、同じ種類、同じ主題の見出しで共通の図鑑に機械的に写し、同じ照合を通してから置く。図鑑に登録されていない項目は写せない。元のプロジェクトの項目と引用は残る。

`common_entries.py candidates` は、共通に移す候補を 2 種類だけ挙げる。比べるのは、図鑑に登録された項目（図鑑に id のある控えの項目）だけである。1 つは、いまのプロジェクトの項目のうち general が true のもので、理由は general_words である。もう 1 つは、いまのプロジェクトの項目と別のプロジェクトの項目で、発言の写しが近い組である。近さは写しどうしだけで測る。写しから空白と記号を除いた連続 2 文字の組の集合を作り、組ごとに全項目の写しでの出現の少なさで重み（idf）を付け、共有する組の重みの和を、短い側の写しの組の重みの和で割る。項目の組の近さは写しの組のうち最も近いもので、0.5 以上かつ共有する組が 5 以上なら候補にする（`--threshold`、`--min-shared` で変えられる）。どちらも、既に共通にある項目（共通に写した項目と、共通の項目と写しが近い項目）は除く。

## 9. 古い形式の候補の移行

doc_kind、general、general_words の欄が無い候補（`cand_*.jsonl`）は、`migrate_legacy.py` で指定したプロジェクトの控えに足す。図鑑への登録はこのスクリプトでは行わない。

```
python scripts/migrate_legacy.py --round <名前> [--route <ID の先頭>=<キー> ...] [--project <既定のキー>]
                                 [--kind <種類>] [--mixed first|all] [--dialogs <フォルダ>] [--dry-run] <cand_*.jsonl ...>
```

- 元のファイルごとに回（`<名前>-<ファイル名の幹>`。例 `v3-cand_02`）を作る。回のフォルダには、そのプロジェクトに振り分けた候補を欄を補った形で `cand_01.jsonl` に書き、`scope.json` に用途 `migrate` と元のファイルを書く。台帳には、登録を待つ回として記録する。図鑑への登録は、回を 1 つずつ、取り込みと同じ手順（`check_genten.py --round <回> --start`、登録の担当、`--install`）で行う。
- doc_kind は、`--kind` を渡せばそれに、無ければ applies_to の中で最も前に現れた手がかりの語（論文、発表、スライド、依頼文、返答など）から決め、決められなければ「その他」にする。general は false、general_words は空にする。
- 振り分けは、`--route` を順に試し、evidence を - と空白と # で区切った語のどれかがその先頭で始まれば、そのキーのプロジェクトに入れる。どれにも当たらない候補は既定のプロジェクト（1 節の決め方）に入れる。`--mixed all` は、根拠が複数のプロジェクトにまたがる候補を、そのすべてに入れる。既定の first は、最初に当たった `--route` のプロジェクトだけに入れる。
- 項目の id は `<回>:<候補の id>` で、同じ回は同じプロジェクトに 2 度足さない。取り消しは、プロジェクトごとに `install_round.py --remove <回> --project <キー>` で行う。
- `--dialogs` に対話の抜き出しのフォルダを渡すと、根拠の発言の時刻を引いて控えに書く。`--dry-run` は振り分けの結果だけを表示する。
- 移行の回はセッションの取り込み済みの範囲を持たないので、移した候補のもとになったセッションを `extract_dialog.py --round` に渡すと、その発言は範囲に入る。
