# 文言と発表原稿（日本語）

スライドの文言と発表原稿のうち、スライドという形に固有の書き方をまとめた。文の基準（主語、指示語、比喩、用語の一貫性）は、文体の層（buntai-seyo）の第 1 節と「発表（スライドと台本）」の項にある。事実に意味を添えることと、次のスライドへのつなぎは、論述の層（ronjutsu-seyo）にある。このファイルは、それらと合わせて読む前提で書いている。書く前に 1〜4 を読む。書いたあとの確認と、別のエージェントへの確認の依頼には 5 を使う。時間に合わせて削るときは 6 を使う。

ここでは、そのスライドの事実が問題を示すものを−、対処が有効であることを示すものを＋と呼ぶ（論述の層の 3.2）。発表は−と＋の反転で進み、反転のない事実の並びは、聞き手には羅列に聞こえる。

## 1. スライドの文言

- 見出しは主語と述語のある一文にする（`structure.md` の 2）。見出し以外の文言は短い句にして、文で説明したい内容は発表原稿に回す。
- 見出しと、数行にわたる文言は、意味の切れ目で手動で改行する。自動の折り返しに任せると、語の途中で切れたり、1 語だけの行ができたりする。
- スライドに出る数、名前、記号は元の資料と照合する。数は元の資料の値をそのまま使う。
- 見出しに数が出るとき（「4 つの」「5 つのうち 4 つで」）は、スライド上の要素の数と一致しているかを確かめる。

## 2. 発表原稿の構成

スライド 1 枚分の発表原稿は、次の 4 つで構成する。

1. 見出しの言い換え。見出しと同じ主語、同じ＋−で別の言葉にし、見出しをそのまま読み上げない。
2. 図や表の読み方。何が並んでいて、どこを見ればよいかを述べる。
3. ＋か−かを示す一文。そのスライドの事実が、聞き手にとって何が良いのか、何が困るのかを述べる。
4. 次のスライドへつなぐ一文。そのスライドに表示されている内容から作る（論述の層の 3.1）。たとえば、＋で締めたあとに次のスライドの問題を問いの形で示すと、次のスライドへ入りやすい。

4 つすべてが毎回必要なわけではない。証拠を並べる区間のように、各スライドが自分の問いで始まり＋で完結する場合は、4 を省いてよい。

実例（スライドは、見出しと、目的・ツールの名前・返る内容を並べた表）

> 見出し: alphaXiv MCP を使うと、論文の検索から実装の閲覧までをエージェントとの会話の中で行える
>
> 発表原稿: alphaXiv MCP を使うと、利用者は論文の検索から実装の閲覧までをエージェントとの会話の中で行えます。表は目的ごとのツールの名前とツールの返す内容の一覧です。たとえば discover_papers はトピックに合う候補を 5 件から 15 件、順位をつけて返します。ツールは全部で 21 個あり、そのうち検索と分析のツールは利用枠を消費します。次は実験を実行するための orx の導入です。

この例では、第 1 文が見出しの言い換えで、主語（利用者）を追加している。表は「左が目的、右が内容」と位置で指さず、何の一覧かで述べている。読み上げる数（5 件から 15 件、21 個）は、スライドに表示されている数である。利用枠の話は聞き手にとって制約を示す−の事実だが、聞き手の判断に必要なので本編に置いている。

### 図や表は、位置ではなく内容で指す

「右の図」「下の表」「左の列」と言うと、聞き手は場所を探す。「精度の推移を示す線」「目的ごとの機能の一覧」のように、それが何であるかで述べる。投影の向きや配布した紙では、位置が変わることもある。

## 3. 文の修正例

初版の文を書き直した例である。初版の問題は、いずれも文体の層の第 1 節の基準に当たる。

| 初版 | 修正後 | 初版の問題 |
|---|---|---|
| どちらも alphaXiv が公開している。普段のコーディングエージェントにそのまま足せる。 | alphaXiv MCP と orx の両方を使うと、利用者は論文の調査から実験の実行までを同じエージェントで進められます。 | 主語がない。「足せる」は比喩で、何ができるのかが分からない |
| 仮説を実験の木にして走らせ、結果で次を決める。 | orx を使うと、エージェントはベースラインから実験を派生させ、run の結果ごとに次の操作を選んで実験を進められます。 | 「木にして走らせ」は比喩。誰が何をするのかが分からない |
| Codex では API キーが公式の推奨。Codex 側の不具合で、ブラウザでのサインインがいまは通らない。 | Codex で API キーを使うのは、現在 Codex の不具合でブラウザでのサインインが失敗するためです。alphaXiv も API キーでの認証を勧めています。 | 体言止めで文が切れている。理由と結論の順が逆で、「公式」が誰なのかも分からない |
| （カードの題）管理計算は前払い（カードの本文）残高から引かれる。自前の計算資源は残高を使わない。 | ローカルの実験にはログインも残高も要らず、OpenResearch の計算資源を使う場合に orx login と前払いの残高が要ります。 | 短い文の羅列で、どの場合に何が必要なのかがつながっていない |

## 4. 日本語で注意する点

次の点は文体の層の第 1 節と同じ基準で、発表原稿にも適用する。

- 主語を書く。指示語は、指す先が一つに決まるときだけ使う。
- 比喩の動詞を使わない。定着した漢語を和語に言い換えない。
- ツール、設定、データを主語にして「決める」「可能にする」「語る」と書かない（擬人化）。

発表原稿に固有の点は次のとおりである。

- 受け身の文を続けない。誰が何をするのかが分からなくなる。
- 用語が最初に出るときは「日本語 (English)」の形にして、以降は日本語だけにする。
- 英字と数字の前後に半角の空白を入れ、数字は半角にする。表記は全スライドで統一する。
- 見出しと 1 行の句では、間を作るだけの読点を入れない（「大事なのは、」「新しい手順では、」のあと）。条件、逆接、理由の切れ目の読点と、名詞を並べるときの読点は残す。
- スライドは常体、発表原稿は敬体にすると話しやすい。1 つの発表の中では統一する。
- 文末が「ます」ばかり続くと単調に聞こえる。一覧や定義は「〜です」で述べて変化をつける。ただし文末を変えるために、文の意味を変えない。

## 5. 点検の問い

点検の中心は、論述の層の第 5 節（読み直しの問い）と文体の層の基準である。ここには、スライドと発表原稿の対応に固有の問いだけを置く。問題のある文を見つけても、その文だけを直さない。そのスライドの主張と、前後のスライドとのつながりから見直す（論述の層の第 2 節）。

- このスライドの見出しは一文で主張を述べているか。
- 発表原稿の第 1 文は、見出しと同じ主語、同じ＋−か。
- 各スライドの事実は、＋か−のどちらかに働いているか。−と＋の反転で話が進んでいるか。
- 図や表を、位置で指していないか。
- 読み上げる数は、スライドに表示されている数か。

## 6. 長さの決め方

発表原稿の長さを字数の目標から決めない理由は、論述の層の 3.9 にある。発表に固有の手順は次のとおりである。

- 段階ごとに承認を待つ場合は、先に「話す内容の上限」を箇条書きにして利用者と合意し、そこから削って発表原稿にする。上限をそのまま文にすると長すぎる。
- 時間は、発表する本人に測ってもらう。話す速さは人によって違う。
- 時間に収めるために削るときは、文ごとに次を確かめる。答えと例を残し、＋にも−にも働かない説明から削る。
  - 前のスライドの問いへの答えか
  - 主張を支える例か
  - その語が最後に出たスライドから離れていないか
  - ＋か−のどちらかに働いているか
- 内容を保ったままでは削れないときは、文を縮めるのをやめる。スライドを予備に移す案を、時間の合計と一緒に示す。
