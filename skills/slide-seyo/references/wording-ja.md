# 文言と発表原稿（日本語）

スライドの文言と発表原稿のうち、スライドという形に固有の書き方をまとめた。主語、指示語、比喩、用語の一貫性のような文の基準は文体の層（buntai-seyo）の第 1 節と「発表（スライドと台本）」の項に、事実に意味を添えることと次のスライドへのつなぎは論述の層（ronjutsu-seyo）にあり、このファイルはそれらと合わせて読む前提で書いている。書く前に 1〜4 を読み、書いたあとの確認と、別のエージェントへの確認の依頼に 5 を使い、時間に合わせて削るときに 6 を使う。

目次

1. スライドの文言
2. 発表原稿の構成
3. 文の修正例
4. 日本語で注意する点
5. 点検の問い
6. 長さの決め方

## 1. スライドの文言

- 見出しは、主語と述語のある一文にする（`structure.md` の 2）。見出し以外の文言は短い句にして、文で説明したい内容は発表原稿に回す。
- 見出しと、数行にわたる文言は、意味の切れ目で手動で改行する。自動の折り返しに任せると、語の途中で切れたり、1 語だけの行ができたりする。
- スライドに出る数、名前、記号は元の資料と照合し、数は元の資料の値をそのまま使う。
- 見出しに数が出るとき（「4 つの」「5 つのうち 4 つで」）は、スライド上の要素の数と一致しているかを確認する。

日本語の見出しは「、」のあとで 2 行に分けると読みやすいという感触があるが、根拠は 2026-11-13 のデッキ 1 件だけなので試案として扱い、意味の切れ目で分けるという考え方の方を使う。

## 2. 発表原稿の構成

スライド 1 枚分の発表原稿は、次の 4 つで構成する。ここでいう向きは、そのスライドの事実が主張にとって問題を示すのか、対処が効くことを示すのかの別であり、意味を添える理由は論述の層の 3.2 にある。

1. 見出しの言い換え。見出しと同じ主語、同じ向きで別の言葉にし、見出しをそのまま読み上げない。
2. 図や表の読み方。何が並んでいて、どこを見ればよいかを述べる。
3. 向きを決める一文。そのスライドの事実が、聞き手にとって何が良いのか、何が困るのかを述べる。
4. 次のスライドへ渡す一文。そのスライドに表示されている内容から作る（論述の層の 3.1）。

4 つすべてが毎回必要なわけではなく、証拠を並べる区間のように、各スライドが自分の問いで始まって良い話で完結する場合は 4 を省いてよい。

実例（2026-11-13 のデッキ。スライドは、見出しと、目的・ツールの名前・返る内容を並べた表）

> 見出し: alphaXiv MCP を使うと、論文の検索から実装の閲覧までをエージェントとの会話の中で行える
>
> 発表原稿: alphaXiv MCP を使うと、利用者は論文の検索から実装の閲覧までをエージェントとの会話の中で行えます。表は目的ごとのツールの名前とツールの返す内容の一覧です。たとえば discover_papers はトピックに合う候補を 5 件から 15 件、順位をつけて返します。ツールは全部で 21 個あり、そのうち検索と分析のツールは利用枠を消費します。次は実験を実行するための orx の導入です。

この例では、第 1 文が見出しの言い換えで、主語（利用者）を追加している。表は「左が目的、右が内容」と位置で指さず、何の一覧かで述べている。読み上げる数（5 件から 15 件、21 個）は、スライドに表示されている数である。利用枠の話は聞き手にとって制約を示す事実だが、聞き手の判断に必要なので本編に置いている。

### 図や表は、位置ではなく内容で指す

「右の図」「下の表」「左の列」と言うと、聞き手は場所を探す。「精度の推移を示す線」「目的ごとの機能の一覧」のように、それが何であるかで述べる。投影の向きや配布した紙では、位置が変わることもある。

## 3. 文の修正例

実例（2026-11-13 のデッキ）。初版は日本語についてもユーザーから作り直しを求められ、書き直した版が修正後の列である。初版の問題は、いずれも文体の層の第 1 節の基準に当たる。

| 初版 | 修正後 | 初版の問題 |
|---|---|---|
| どちらも alphaXiv が公開している。普段のコーディングエージェントにそのまま足せる。 | alphaXiv MCP と orx の両方を使うと、利用者は論文の調査から実験の実行までを同じエージェントで進められます。 | 主語がない。「足せる」は比喩で、何ができるのかが分からない |
| 仮説を実験の木にして走らせ、結果で次を決める。 | orx を使うと、エージェントはベースラインから実験を派生させ、run の結果ごとに次の操作を選んで実験を進められます。 | 「木にして走らせ」は比喩。誰が何をするのかが分からない |
| Codex では API キーが公式の推奨。Codex 側の不具合で、ブラウザでのサインインがいまは通らない。 | Codex で API キーを使うのは、現在 Codex の不具合でブラウザでのサインインが失敗するためです。alphaXiv も API キーでの認証を勧めています。 | 体言止めで文が切れている。理由と結論の順が逆で、「公式」が誰なのかも分からない |
| （カードの題）管理計算は前払い（カードの本文）残高から引かれる。自前の計算資源は残高を使わない。 | ローカルの実験にはログインも残高も要らず、OpenResearch の計算資源を使う場合に orx login と前払いの残高が要ります。 | 短い文の羅列で、どの場合に何が必要なのかがつながっていない |

## 4. 日本語で注意する点

主語、指示語、比喩の動詞、普通に使う漢語を和語に言い換えないことは、文体の層の第 1 節にある。ツール、設定、データを主語にして「決める」「可能にする」「語る」と書く形は、文体の層の「論文（日本語）」の項が翻訳調と擬人化として扱っており、発表原稿にもその基準を当てる。ここには、それ以外の点を挙げる。

- 受け身の文を続けない。誰が何をするのかが分からなくなる。
- 用語が最初に出るときは「日本語 (English)」の形にして、以降は日本語だけにする。
- 英字と数字の前後に半角の空白を入れ、数字は半角にし、表記を全スライドで統一する。
- 見出しと 1 行の句では、間を作るだけの読点を入れない（「大事なのは、」「新しい手順では、」のあと）。条件、逆接、理由の切れ目の読点と、名詞を並べるときの読点は残す。
- スライドは常体、発表原稿は敬体にすると話しやすい。1 つの発表の中では統一する。
- 文末が「ます」ばかり続くと単調に聞こえるので、一覧や定義は「〜です」で述べて変化をつける。文末を変えるために、文の意味を変えない。

## 5. 点検の問い

点検の中心は、論述の層の第 5 節（読み直しの問い）と文体の層の基準であり、ここにはスライドと発表原稿の対応に固有の問いだけを置く。問題のある文を見つけたときに、その文だけを直さず、そのスライドの主張と前後のスライドとのつながりから見直す理由は、論述の層の第 2 節にある。

- このスライドの見出しは、一文で主張を述べているか。
- 発表原稿の第 1 文は、見出しと同じ主語、同じ向きか。
- 図や表を、位置で指していないか。
- 読み上げる数は、スライドに表示されている数か。

## 6. 長さの決め方

発表原稿の長さを字数の目標から決めない理由は、論述の層の 3.9 にある。発表に固有の手順は次のとおりである。

- 段階ごとに承認を待つ場合は、先に「話す内容の上限」を箇条書きにしてユーザーと合意し、そこから削って発表原稿にする。上限をそのまま文にすると長すぎる。
- 時間は、発表する本人に測ってもらう。話す速さは人によって違う。
- 時間に収めるために削るときは、文ごとに、前のスライドの問いへの答えか、主張を支える例か、その語が最後に出たスライドから離れていないか、その文に向きがあるかを確認し、答えと例を残して、向きのない説明から削る。
- 内容を保ったままでは削れないときは、文を縮めるのをやめ、スライドを予備に移す案を、時間の合計と一緒に提示する。
