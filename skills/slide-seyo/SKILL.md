# slide-seyo

聞き手が前のスライドを見返さずに主張を理解できる発表のスライドを作成するための、作業の手順と検査の道具をまとめたスキルである。モデルはデザインの指定がなければ決まった見た目（淡いクリーム色の背景、小見出しのラベル、同じ形のカードの並び、小さい灰色の文字）に寄りやすく、しかも作成した本人には描画後の崩れが見えない。手順はこの 2 点を前提にしており、主張ごとに証拠の示し方を選んでから作成し、描画した結果を検査スクリプトで測定して可読性の基準を満たすまで修正する。何をどの順で主張するかと、語と文の選び方は、論述の層（ronjutsu-seyo）と文体の層（buntai-seyo）が定めている。このスキルが持つのはスライドという形に固有の基準であり、層を読む場面は「構成案」「作成時の要点」「文言の確認」の各節に書いた。

## 手順

1. 作成前: 既存の基準を探し、構成案をユーザーに提示する。
2. 作成: 主張ごとに証拠の示し方を決めてから、スライドを作成する。
3. 検査: 描画して検査スクリプトを実行し、画像を確認して修正する。文言は書いた本人以外が確認する。
4. 報告: 結果をユーザーに報告する。

会話の文脈が圧縮されたあとに作業を続けるときは、構成案とプロジェクトの決まりを読み直してから進める。圧縮で失われやすいのは、ユーザーと合意した細部だからである。

## 作成前

### 既存の基準を探す

次のものがあれば、このスキルの既定より優先する。優先順位は、ユーザーの指示、プロジェクトの決まり、このスキルの既定の順である。

- ユーザーの指示
- プロジェクトの決まり（`CLAUDE.md`、`AGENTS.md`、`docs/` の決定表や用語表、ユーザーが指定したファイル）
- 会場や所属のテンプレート
- 過去のデッキ

### 構成案

作成を始める前に、構成案をユーザーに提示する。構成案には、依頼から読み取れなかった前提と各スライドの見出しの一覧を書き、依頼の言葉が複数の意味に取れる点（指定された枚数に表紙を含めるか、など）はどう解釈したかを書く。決まった様式はない。

見出しを決める前に、論述の層を、文書の種類を「発表（スライドと台本）」として読む。見出しを順に並べたものが発表全体の論証になるので、問題の定義、そこから生じる問い、結果の並べ方は、スライドを作成する前に決まっていなければならないからである。構成を変えない修正（文言や図だけを直す依頼）では、この時点では読まない。

```
構成案（このまま作成します）

聞き手   研究室のゼミ。このツールを使ったことがない人を含む
目的     2 つのツールを導入して使えるようにする
形式     HTML、7 枚（表紙を含む）、日本語
基準     このスキルの既定。プロジェクトの決まりは見つからなかった

見出し
 2  ツール A とツール B を導入すると、調査と実験をエージェントに任せられる
 3  ツール A は 1 つのコマンドで登録できる
 4  ツール A を使うと、検索から実装の閲覧までを会話の中で行える
 …

前提が違う場合は止めてください。
```

見出しの一覧だけを順に読んで発表の要約になっているかを確認し、なっていなければスライドを作成する前に見出しを直す。既定と違う基準を使うとき（テンプレートの指定がある、発表の種類に合わない）は、何をなぜ変えたかを構成案に書く。

### 確認のタイミング

既定では、構成案を提示したあと、承認を待たずに全スライドを作成する。前提が違っていれば、ユーザーはその時点で止められるからである。次の場合は既定と別の対応をする。

- ユーザーが承認を待つよう指定した場合は、段階ごとに承認を待つ。段階の一覧は `references/stages.md` にある。
- ユーザーが構成案は不要と言った場合は、提示せずに作成する。
- 依頼の内容だけでは構成を決められない場合は、作成を始める前に、任せてよいか、相談したい点があるかを短く尋ねる。

ユーザーが書いた原稿や文書と、プロジェクトの記録（決定の文書、引き継ぎの文書、エージェントのメモリ）は、ユーザーの承認を得てから変更する。

## 作成

### 3 種類の基準

このスキルの基準は性質の違う 3 種類に分かれ、扱い方もそれぞれ違う。

| 種類 | 内容 | 扱い方 |
|---|---|---|
| 可読性の基準 | 文字サイズ、コントラスト、はみ出し、重なり、見出しの行数 | 検査スクリプトで測定し、違反を 0 件にする。デザインの好みとは関係がない |
| 構成の原則 | 見出し、証拠の示し方、スライド間のつながり | 理由つきの既定であり、発表の種類に合わないときは、理由を構成案に書いて変更する |
| デザインの設定値 | 色、フォント、余白 | 差し替えられる。テンプレートやユーザーのデザイン文書があればそれを使い、なければ `references/theme.md` の既定を使う |

可読性の基準の値は次のとおりで、いずれも高さ 7.5 in のスライドでの値である。

- 本文の文字は 18 pt 以上、補足（出典、ページ番号）は 12 pt 以上
- 文字と背景のコントラスト比は 7:1 以上。大きい文字と補足は 4.5:1 以上
- スライドからのはみ出し、テキストの枠からのオーバーフロー、文字どうしの重なりがない
- 見出しは 2 行まで

閾値の理由、投影と手元の画面での違い、検査スクリプトで測定できない項目は `references/legibility.md` にあり、閾値を変更するときに読む。デザインの設定値を差し替えても可読性の検査は同じように実行し、テンプレートを使うときも構成の原則は変えない。

### 作成時の要点

- 見出しには、そのスライドの主張を一文で書く。「結果」「導入方法」のような題目だけの見出しでは、聞き手は図から主張を自分で探すことになる。この書き方をそろえると、見出しを順に読んだものが発表の要約になる。
- 1 枚のスライドには主張を 1 つと、それを支える証拠を 1 つ置き、証拠の示し方は主張から選ぶ。関係や流れなら図、項目どうしの対応なら表、手順ならコマンドや実際の画面、量の比較ならグラフ、聞き手が実物を知らないなら実物の画像を使う。どのスライドも「見出しと表」か「見出しと箇条書き」になっていたら、主張ではなく手元の材料から作成している。選び方と例は `references/structure.md` にある。
- 図は、何を見せたいかを決めてから作成する。決まらないうちに部品を動かすと、動かすたびに別の箇所が崩れる。描き方に迷ったら、imozuru で同じ内容を扱った論文の図や講演のスライドを集め、その慣例に従う。
- スライドの文は短い句にして、説明は発表原稿に回す。スライドと発表原稿が同じ文だと、聞き手は読むことと聞くことを同時にしなければならない。
- 結論のスライドに載せるのは、それまでのスライドに表示した内容だけであり、発表原稿で話しただけの内容は含めない（`references/structure.md` の 6）。
- 出典は他人の主張や画像が出るスライドにだけ置き、位置と書式を全スライドで統一する。
- 1 か所を修正したら、全スライドを見直す。1 つ動かすと余白のバランスが変わり、同じ種類の崩れがほかのスライドにも残っていることが多い。

避けるデザインの一覧と修正前後の例は `references/patterns.md` にあり、作成する前に読む。

スライドの文言と発表原稿を書く前に、文体の層を、文書の種類を「発表（スライドと台本）」として読む。この作業で論述の層をまだ読んでいなければ（文言だけを直す依頼など）、同じ時点で論述の層も「発表（スライドと台本）」として読む。スライドという形に固有の文言の書き方（発表原稿の構成、改行、表記、読み上げる数）は、日本語なら `references/wording-ja.md`、英語なら `references/wording-en.md` にあり、これも同じ時点で読む。

## 検査

作成方法と検査の手順は形式ごとに違うので、使う方だけを読む。

- HTML で作成する: `references/backend-html.md`
- .pptx など、PDF に書き出せる形式で作成する: `references/backend-pdf.md`

どちらも流れは同じである。

1. 検査スクリプトを実行し、違反が 0 件になるまで修正と再実行を繰り返す。
2. 全スライドの画像を確認する。検査スクリプトが測定するのは数値で測れる項目だけなので、配置のバランス、主役と補足の強弱、図が主張を示しているかは画像で確認する。作成した本人はコードを見たあとなので、意図したとおりに見えてしまう。可能なら、別のエージェントに画像だけを渡して確認させる。
3. 修正したら、そのスライドだけでなく全スライドを描画し直して確認する。
4. 文言を確認する（次の節）。

### 文言の確認

書いた本人は、自分の文の論理の飛躍や曖昧な主語に気づきにくいので、次の順で確認する。

1. スライドの文言と発表原稿を、論述の層の第 5 節（読み直しの問い）と、文体の層の第 1 節および「発表（スライドと台本）」の項の基準で点検し、`references/wording-ja.md`（または `wording-en.md`）の点検の問いを加える。日本語の表記や言い回しの機械的な検査には、yomiyasu の検査スクリプトを任意の道具として使ってよいが、yomiyasu の本文は読み込まない。
2. 書いた本人以外のエージェントに、スライドの文言と発表原稿、元の資料、点検の問い（論述の層の第 5 節と、`wording-ja.md` または `wording-en.md` の点検の問い）だけを渡して、指摘させる。自分の結論や自己評価は渡さず、修正はさせずに指摘だけを返させる。
3. 指摘を採用するかどうかは、メインエージェントが決める。事実の訂正は元の資料で確認してから採用し、言い切りを弱めるだけの提案はユーザーに判断を仰ぐ。

別のエージェントに作業を委譲するときは、delegate-seyo の手順（指示書の書き方、結果の確認）に従う。機械的に測定できることは検査スクリプトで行い、数回の操作で済むことは自分で行う。

## 報告

ユーザーへの報告は次の順で書く。

1. 作成したものと、その場所。重大な問題が残っていれば、最初に書く。
2. 構成案から変更した前提。
3. 検査の結果。違反の件数、修正した項目、描画に使ったツールを書き、「検査した」「問題なかった」だけで済ませない。
4. 残っている課題と、その次の対応。

残っている課題を「〜は確認していない」「〜は測定していない」で終えると、読む人は、分かっているならなぜやらないのかと考える。そこで、まず自分で解決できる手段を試し、それでも残ったものは、解決に必要なものをユーザーへの依頼として書く（「PowerPoint で PDF に保存して渡してもらえれば、文字サイズと重なりを測定できる」のように）。事実は削除せず、同じ事実を言い訳ではなく次の対応として書く。

## 資料の一覧

| ファイル | 読む場面 |
|---|---|
| `references/structure.md` | 構成案を書く前、スライドの構成を決めるとき |
| `references/patterns.md` | 作成する前、画像を確認して修正するとき |
| `references/wording-ja.md`／`wording-en.md` | スライドの文言と発表原稿を書く前、文言を確認するとき |
| `references/theme.md` | デザインの設定値を決めるとき、テンプレートに差し替えるとき |
| `references/legibility.md` | 閾値を変更するとき、検査結果の意味を確認するとき |
| `references/stages.md` | ユーザーが段階ごとの承認を指定したとき |
| `references/backend-html.md` | HTML で作成するとき |
| `references/backend-pdf.md` | .pptx など、PDF に書き出せる形式で作成するとき |
| `references/sources.md` | 基準の根拠を確認したいとき、ユーザーに根拠を聞かれたとき |

人が読むための説明は `README.md` にあり、作業のために読む必要はない。
