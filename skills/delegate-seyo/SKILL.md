# delegate-seyo

委譲した作業の品質は、指示書と結果の確認で決まる。委譲先はこちらの会話もユーザーの意図もそれまでに判明したことも知らず、指示書に書かれたことだけをもとに作業する。委譲する側も委譲先の作業の過程を見ることはできず、報告だけをもとに結果を判断する。情報が欠落するのは指示書と報告の 2 か所であり、このスキルは指示書の書き方と報告の確認の手順を定める。

委譲しても責任は移らない。委譲先の結果が誤っていれば、それを使った自分の成果物も誤るので、委譲するのは作業に限り、設計と品質の確認は自分で行う。

## 1. 委譲するかどうかを決める

サブエージェントは費用の大きな部分を占めるので、委譲の前に次の順で判断する。

1. 機械的に測定できる作業と、毎回同じ処理になる作業はスクリプトにし、エージェントに繰り返させない。スクリプトなら実行のたびにエージェントの費用がかからず、同じ入力に同じ結果を返す。
2. 数回の操作で済む作業と、見るべき場所が分かっている作業は自分で行う。指示書を書いて結果を確認する手間のほうが、作業そのものより大きいからである。
3. 次のいずれかに当てはまる作業は委譲する。
   - 互いに独立した作業が複数あり、並行して進められる
   - 大量の資料を読む必要があり、必要なのは結論だけである
   - 自分が書いたものを、書いた本人以外に確認させたい
   - ユーザーが、主な作業を止めずに調べてほしいと言っている

指示書を明確に書けないなら、まだ委譲できる段階ではない。書けないのは、自分が作業を理解していないからである。

委譲先のモデルは作業の性質で選ぶ。事実の収集や手順の決まった作業は軽いモデルで足り、判断を要する確認や、資料を読み比べて矛盾を見つける作業は上位のモデルに委譲する。

## 2. 指示書を書く

委譲先は作業をこなす能力を持つが、こちらの文脈を持たず、指示書にないことは補えない。そのため指示書には次の項目を書く。ひな形と例は `references/brief.md` にあり、初めて書くときと長い指示書を書くときに読む。

| 項目 | 書かない場合に起きること |
|---|---|
| 目的と、結果の使い道 | 委譲先は何を優先すればよいかを判断できず、形式だけ合った答えを返す |
| 読む資料と、読む順番 | 関係の薄い資料を読み、必要な資料を読まない |
| 書き込んでよいファイルと、変更してはいけないファイル | 範囲外のファイルを書き換える |
| 読むだけか、修正してよいか | 「確認して」を修正の許可と受け取り、本体を書き換える |
| ユーザーの言葉（原文のまま） | こちらの言い換えを経て、ユーザーの意図が伝わらなくなる |
| すでに分かっていること、すでに除外したこと | 同じことを調べ直す |
| 完了の証拠 | 「確認しました」だけが返る |
| 報告の形式（言語、長さ、順番、確認できなかったことの分け方） | 報告が長くなり、こちらのコンテキストを消費する |
| 停止する条件と、判断が必要なときの対応 | 判断が必要な場面で、独断で進める |

指示書の文章は、その会話で初めて指示書を書く前に論述の層（ronjutsu-seyo）と文体の層（buntai-seyo）を読み、その基準で書く。文書の種類は、どちらの層でも「AI 向けの文書（指示書、スキルの本体）」である。目的と理由の書き方、長さの指定の仕方、第三者としての確認を依頼するときに何を渡すかは、論述の層のこの種類の項が扱う。

承認、結果の置き場所、指示書の保存、プロジェクトの決まりは、委譲の手順として次のように扱う。

- 承認を要する行為は、「原稿のファイルを書き換える前に停止して報告する」のように具体的に名指す。「慎重に」のような漠然とした書き方では、委譲先はどの行為に承認が要るかを判断できず、あらゆることを確認しに戻ってくる。
- 長い結果は委譲先にファイルへ書かせ、報告は要点に限らせる。報告はそのままこちらのコンテキストに入るからである。
- 長い指示書と繰り返し使う指示書はファイルに書き、起動のプロンプトではそのファイルを指定するだけにする。何を依頼したかを、あとでユーザーも自分も確認できる。
- プロジェクトに決まり（作業の規約、用語の一覧、変更してはいけない場所）があれば、関係する項目を指示書に写すか、読む資料として指定する。委譲先は、こちらが読んだ規約を読んでいない。

## 3. 並行して委譲するとき

並行する委譲先は互いの作業を知らないので、書き込みの衝突と作業の重複は委譲する側が防ぐ。

- 書き込むファイルを委譲先ごとに分け、同じファイルを 2 つのエージェントに編集させない。
- 互いの結果に依存する作業は並行して進めない。後の作業が、前の作業の結果のないまま進むことになる。
- 委譲した作業を自分でも始めず、結果を待つ。同じ作業に費用が二重にかかり、2 つの結果が食い違えば突き合わせる手間も生じる。
- 結果が届く前に、結果を予想してユーザーに報告しない。予想は結果ではなく、外れればユーザーは誤った報告をもとに判断することになる。

## 4. 結果を受け取ったら確認する

委譲先の報告は、事実ではなく主張として受け取る。委譲先はこちらより少ない文脈で作業しており、誤りも確かな発見と同じ調子で書いて返すからである。結果を成果物に使う前に `references/acceptance.md` を読み、次の順で確認する。

1. 完了の証拠が、依頼したとおりに付いているかを確認する。付いていなければ委譲先に提出させる。
2. 範囲外のファイルを変更していないかを確認する。ファイルを書く作業を委譲したときは差分で確認する。git で管理している場所では、同梱の `scripts/scope_check.py` で、変更されたファイルが許可した範囲に収まっているかを一覧にできる。
3. 結論を左右する主張を元の資料で確認する。すべてを確認する必要はなく、自分の成果物に入れる数、名前、引用と、判断の根拠になる事実を選ぶ。
4. 成果物（図、文書、コード）は、描画するか実行して実物を確認する。
5. 委譲先自身が「確認できなかった」と書いたものと、ほかの資料から写しただけのものを区別しておく。

レビューや確認を委譲したときは、指摘を 1 件ずつ、採用するかどうかを決める。事実の誤りの指摘は、元の資料で確認してから採用する。言い切りを弱めるだけの提案と、ユーザーが決めたことと食い違う提案は、ユーザーに判断を仰ぐ。採用しなかった指摘は理由とともに記録する。

修正が必要なときは、可能なら同じ委譲先に、何がどう違っていたかを具体的に伝えて修正させる。その委譲先はすでに文脈を持っているからである。

## 5. ユーザーに伝える

ユーザーは報告をもとに、どの結論をそのまま使い、何を自分で補うかを決める。委譲の結果をユーザーへの報告にまとめるときは、文書の種類を「報告、説明の返答」として論述の層と文体の層を読み、その基準で書く（その会話ですでに読んでいれば読み直さない）。委譲を経た報告に固有の項目は次のとおりである。

- 自分で確認したことと、委譲先がそう報告しているだけのことを区別して伝える。
- 確認できなかったことは「確認していない」で終わらせず、確認に必要なものをユーザーへの依頼として書く。
- 委譲した作業が失敗したときは、失敗したと伝え、何を変えてやり直すかを添える。

## 資料

| ファイル | 読む場面 |
|---|---|
| `references/brief.md` | 指示書を書くとき（ひな形、良い例と悪い例） |
| `references/acceptance.md` | 結果を成果物に使う前と、レビューの指摘を採用するかどうかを決めるとき |
| `scripts/scope_check.py` | ファイルを書く作業を委譲したあと、範囲外の変更を確認するとき |

人が読むための説明は `README.md` にあり、作業のためには読まなくてよい。
