# 指示書のひな形と例

## 1. ひな形

項目は作業に必要なものだけを使う。短い調査なら、目的、読む資料、報告の形式の 3 つで足りる。ファイルを書く作業と成果物に直接入る作業では、範囲の指定や完了の証拠の欠けがそのまま成果物の誤りになるので、すべての項目を書く。

```
（1 行目）何を依頼するか。読むだけか、書き込んでよいか。

## 目的
この作業が何の一部で、結果を何に使うか。ユーザーが何を重視しているか。

## ユーザーの言葉
（関係する発言を、言い換えずに原文のまま書く。なければ省略する）

## すでに分かっていること
調査済みのこと、除外したこと。調べ直さなくてよいこと。
（第三者としての確認を依頼するときにこの欄へ何を書くかは、論述の層の「AI 向けの文書（指示書、スキルの本体）」の基準による）

## 資料
読む資料と、読む順番。それぞれが何であるか。
読まなくてよい資料、開いてはいけない資料。

## 作業の内容
成果物ごとに、何を、どの形式で作成するか。
判定の基準があるなら、数値で書く。

## 書き込んでよい場所
書き込んでよいファイルやフォルダ。それ以外は変更しない。

## 守ること
プロジェクトの決まりのうち、この作業に関係するもの。
承認が必要な行為（具体的に書く）。

## 完了の証拠
報告に付けるもの（実行した出力、件数、ファイルの一覧）。
うまくいかなかったこと、判定の精度が低い箇所も、隠さずに書かせる。

## 報告の形式
言語、長さ、順番。長い結果をどのファイルに書くか。
確認できなかったことは、推測で埋めず、分けて書く。
判断に迷って決めたことは、理由と一緒に先頭に書く。

## 停止する条件
停止して報告してほしい場面。それ以外の場面では、近い形で進めて、何を変えたかを報告する。
```

## 2. 悪い例と良い例

### 調査を委譲する

悪い例

```
このライブラリの認証まわりを調べて、まとめてください。
```

委譲先は何のために調べるのかを知らないので、広く浅い概要を返す。どこまでが確認した事実で、どこからが推測なのかも、報告からは区別できない。

良い例

```
読むだけの調査です。ファイルは変更しないでください。

## 目的
社内向けの導入手順書に、このライブラリのトークンの更新手順を 1 節で載せます。
手順書を読むのは、このライブラリを使ったことがない運用の担当者です。
誤った手順を載せると本番環境の認証が止まるので、公式の文書で確認できた事実だけが必要です。

## すでに分かっていること
トークンの有効期限が 1 時間であることは確認済みです。調べ直さなくて構いません。

## 資料
公式の文書の「認証」の章と、リポジトリの examples フォルダ。
個人のブログや質問サイトは、公式の文書で確認できたときだけ使ってください。

## 作業の内容
1. トークンを更新する手順（呼び出す関数、引数、戻り値）。
2. 更新に失敗したときに起きることと、公式が勧める対処。
3. 更新を自動で行う設定があるか。

## 完了の証拠と報告の形式
事実ごとに、出典の URL を付けてください。
公式の文書で確認できなかった項目は「未確認」と書き、推測で埋めないでください。
日本語、400 語以内。番号は上の 1〜3 の順にしてください。
```

### 第三者としての確認を委譲する

悪い例

```
この報告書をレビューしてください。数値は元の表で全部確認済みで、
結論も妥当だと考えていますが、念のため見てください。
```

「確認済み」「妥当」という自分の結論を伝えているので、委譲先はそれを追認する。「念のため」と言われた作業も、念のための深さでしか行われない。

良い例

```
報告書の数値と主張を、元の表と照合して確認してください。読むだけで、修正はしないでください。

## 目的
この報告書は、来週の予算の判断に使われます。数値が 1 つ違うと判断が変わります。

## 資料
report.md（確認する対象）と、data/ の下の 3 つの表（元のデータ）。
ほかのファイルは、この確認には使いません。

## 作業の内容
報告書の数値と、比較や最上級の主張（「最も多い」「上回る」など）を 1 つずつ取り出し、
元の表から計算し直して照合してください。
元の表から導けない主張、表より強く述べている主張も探してください。

## 報告の形式
食い違いだけを、重要な順に書いてください。各項目に、報告書の文、元の表の値、計算の過程を付けてください。
問題のなかった数値は並べず、最後に「照合した数」だけを書いてください。
確認できなかったものは、食い違いに混ぜず、別に分けてください。
```

### ファイルを書く作業を委譲する

悪い例

```
検査のスクリプトを作って、動くようにしておいてください。
```

良い例に含めるもの

- 書き込んでよいフォルダと、変更しないフォルダ。
- 出力の形式（ほかのスクリプトと統一するなら、その形式）。
- 完了の証拠として、自己テストの出力と、実物に対する実行結果を貼り付けさせること。
- うまく実装できなかった項目と、誤検出が起きそうな場面を、隠さずに挙げさせること。
- 指定を実現できないと分かったときの対応（停止するのか、近い形で進めて報告するのか）。

## 3. 書いたあとに確認すること

- この指示書だけを渡されたとして、自分は作業を始められるか。
- 書き込んでよい場所と、読むだけか修正してよいかが、1 行目か冒頭にあるか。
- 報告の長さを決めたか。
- 文章が、書く前に読んだ論述の層（ronjutsu-seyo）と文体の層（buntai-seyo）の基準を、SKILL.md の 2 節で指定した文書の種類について満たしているか。
