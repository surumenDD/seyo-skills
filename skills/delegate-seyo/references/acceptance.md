# 受け取った結果の確認方法

委譲先の報告を自分の成果物に使う前の手順である。目的はすべてを疑うことではなく、結果のうちどれを確認すれば足りるかを選ぶことにある。

## 1. 何を確認するかを選ぶ

確認する範囲は、結果が誤っていた場合の損害の大きさで決める。

| 結果の使い道 | 確認する範囲 |
|---|---|
| 自分が次に読む場所の見当をつけるだけ | 確認しなくてよい。読めば分かる |
| ユーザーへの報告に、事実として書く | その事実を、元の資料で確認する |
| 論文、発表、公開する文書に入る数や引用 | 1 つずつ、元の資料で確認する |
| ファイルを書き換える作業 | 差分をすべて読む |
| 取り消せない操作につながる判断 | 根拠を自分で読み直す |

## 2. 報告に含まれやすいもの

委譲先の報告には次の種類のものが混ざるので、見分けて扱いを変える。

| 種類 | 見分け方 | 扱い |
|---|---|---|
| 確認済みの事実 | 出典、実行した出力、行番号が付いている | 結論を左右するものを抜き取って確認する |
| ほかの資料から写したもの | 「〜によれば」「〜の報告では」と書かれている。委譲先がさらに別のエージェントに委譲し、その結果を写していることもある | 元の資料をたどる。たどれなければ、未確認として扱う |
| 推測 | 「〜と思われる」「おそらく」と書かれているか、出典がないのに言い切っている | 事実として使わない |
| こちらの見立ての追認 | 指示書に書いた見立てが、新しい根拠なしにそのまま返っている | 根拠を提出させる |
| 範囲外の作業 | 依頼していない修正、依頼していない提案 | 修正は差分で確認し、不要なら元に戻させる |
| 行番号や件数 | もっともらしい数が並んでいる | その数を自分の成果物に入れるなら、数え直す |

委譲先が「すべては確認していない」「この部分は別の報告から写した」と自分で書いている部分は、読み飛ばさず、未確認として扱う。

## 3. 手順

1. 完了の証拠を確認する。指示書で求めたものが付いているかを見て、「テストは通った」と書いてあるだけで出力がなければ、出力を提出させる。
2. 範囲を確認する。ファイルを書く作業なら、何が変更されたかを差分で確認する。git で管理している場所では、次のように実行すると、変更されたファイルのうち許可した範囲の外にあるものが一覧になる。

   ```
   python scripts/scope_check.py --allow "docs/report/**" --allow "scripts/check_*.py"
   ```

   git で管理していない場所では、委譲する前にファイルの一覧と更新日時を記録しておき、あとで比較する。
3. 結論を左右する主張を確認する。1 節の表で選んだ範囲を元の資料で確認し、委譲先が挙げた出典を開いて、その箇所に本当にそう書いてあるかを見る。
4. 実物を確認する。図や文書は描画し、コードは実行する。委譲先の「動いた」は、委譲先の環境と入力での結果にすぎない。
5. 食い違いを委譲先に伝える。何が、どの資料と、どう違っていたかを具体的に伝えて修正させる。原因が指示書の書き方にあった場合は、次の指示書で改める。

## 4. レビューの指摘を採用するかどうか

確認やレビューを委譲すると指摘の一覧が返ってくるので、1 件ずつ判断する。成果物が文書の場合、伝わりにくさと言い切りの強さについての指摘の採否は、その文書の種類にあたる項を論述の層（ronjutsu-seyo2）と文体の層（buntai-seyo）で読み、その基準で判断する。

| 指摘の種類 | 扱い |
|---|---|
| 事実の誤り（数、名前、引用、手順） | 元の資料で確認し、指摘が正しければ採用する |
| 伝わりにくさ、曖昧さ | 聞き手や読み手の立場で読み直し、問題があれば採用する。修正の方法は、委譲先の案に従わなくてよい |
| 言い切りを弱める提案（「〜の可能性がある」に変える、断り書きを追加する） | 根拠の範囲が実際に足りないなら、主張の範囲を言い直す。足りているなら採用しない。迷う場合はユーザーに尋ねる |
| ユーザーが決めたことと食い違う提案 | 採用しない。ただし、ユーザーの決定に事実の誤りがあると考えたら、ユーザーに伝える |
| 元の資料の言い回しに合わせる提案 | 事実が変わるなら採用する。言い回しだけの違いなら、成果物の目的に照らして決める |
| 文脈を知らないことによる指摘 | 採用しない。ただし、読み手も同じ箇所で迷わないかを検討する |

採用したかどうかは一覧にして記録し、採用しなかった指摘には理由を付ける。ユーザーに見せるときは、採用した数と採用しなかった数だけでなく、判断が分かれた指摘を具体的に示す。

委譲先は文脈が少ないので、その指摘は判断の材料であって決定ではない。一方で、文脈が少ないからこそ委譲先は初めて読む人と同じ見方ができ、「説明が必要」という指摘はその意味で重要である。

## 5. ユーザーへの伝え方

報告の文章は、SKILL.md の 5 節のとおり、文書の種類を「報告、説明の返答」として論述の層と文体の層の基準で書く。そのうえで、委譲を経た報告では次の点を扱う。

- 自分で確認したことと、委譲先の報告のままのことを区別する。
- 確認できなかったことは、次の対応と一緒に書く。たとえば「元の表が手元にないため、3 つの数は確認できていない。表の場所を教えてもらえれば照合する」と書く。
- 委譲した作業で起きた、ユーザーが知るべき副作用（何かが更新された、何かがインストールされた）は、報告の中で伝える。
