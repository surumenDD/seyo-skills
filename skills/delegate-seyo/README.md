# delegate-seyo

作業をサブエージェントや別のエージェントに委譲するときの、指示書の書き方と結果の確かめ方を定めたスキルです。

このファイルは人が読むための説明です。エージェントが読むのは `SKILL.md` です。

## 何のためのスキルか

エージェントに作業を委譲すると、次のような失敗が起きます。

- 「確認して」と頼んだのに、本体を書き換えられた。
- 「確認しました、問題ありません」とだけ返ってきた。
- レビューを頼んだら、こちらの結論を追認する報告が返ってきた。
- 報告の数字をそのまま使ったら、委譲先も別の報告から写しただけだった。

原因の多くは委譲先の能力ではなく、指示書の欠落と、受け取る側の確認の不足にあります。このスキルは指示書と結果の確認の二か所について手順を定めます。

## 使い方

名前を出して頼みます。

```
/delegate-seyo この調査を 3 つに分けて、並行で調べさせて
```

```
delegate-seyo の手順で、この報告書の数値を別のエージェントに確認させて
```

slide-seyo の手順も、別のエージェントに委譲する場面でこのスキルを使うよう指示します。

## エージェントがすること

| 場面 | すること |
|---|---|
| 委譲する前 | 委譲するかどうかを決める。機械的に測定できる作業はスクリプトにし、数回の操作で済む作業は自分で行う |
| 指示書を書くとき | 目的、読む資料、書き込んでよい場所、読むだけか修正してよいか、完了の証拠、報告の形式を書く |
| 並行して委譲するとき | 書き込むファイルを委譲先ごとに分ける。委譲した作業を自分でも始めず、結果を待つ |
| 結果を受け取ったとき | 範囲外のファイルを変更していないか、結論を左右する主張が元の資料と一致するかを確かめる |
| 利用者に伝えるとき | 自分で確かめた内容と、委譲先がそう報告しているだけの内容を区別して伝える |

## プロジェクトの決まりを委譲先に伝える

プロジェクトに作業の決まりがあれば、`CLAUDE.md`、`AGENTS.md`、`docs/` の下の文書に書いておきます。決まりとは、変更してはいけないフォルダ、用語、承認が必要な操作などです。エージェントは関係する項目を指示書に写して委譲先に渡します。依頼のときにファイルを指定してもかまいません。

## 同梱のスクリプト

`scripts/scope_check.py` は、委譲した作業が許可した範囲の外のファイルを変更していないかを一覧にします。git で管理しているフォルダで使います。Python の標準ライブラリだけで動きます。

```
python scripts/scope_check.py --allow "docs/report/**" --allow "scripts/check_*.py"
python scripts/scope_check.py --selftest
```

このスクリプトが確かめるのは、どのファイルが変更されたかだけです。変更の内容は差分で確かめます。

## このスキルが扱わないこと

- 指示書と利用者への報告の文章の基準。論述の層（ronjutsu-seyo）と文体の層（buntai-seyo）が定めます。エージェントは指示書と報告を書く前に、文書の種類を指定して二つの層を読みます。二つの層が入っていない置き場では、このスキルの手順と検査だけで進めます。
- エージェントを起動するツールの操作方法。使っているツールの手引きに従ってください。
- 使うモデルの名前。名前は時期によって変わるので、このスキルには書いていません。書いてあるのは、作業の性質で選ぶという考え方だけです。事実の収集には軽いモデルを、判断を要する確認には上位のモデルを使います。

導入、一覧に名前だけを出す設定、削除の手順は[導入の手引き](../../docs/install.md)にあります。

## ファイルの構成

```
delegate-seyo/
├─ SKILL.md                  エージェントが読む本体
├─ README.md                 このファイル
├─ references/
│  ├─ brief.md               指示書のひな形と、良い例と悪い例
│  └─ acceptance.md          結果の確かめ方と、レビューの指摘の扱い
└─ scripts/
   └─ scope_check.py         範囲外の変更の一覧
```
